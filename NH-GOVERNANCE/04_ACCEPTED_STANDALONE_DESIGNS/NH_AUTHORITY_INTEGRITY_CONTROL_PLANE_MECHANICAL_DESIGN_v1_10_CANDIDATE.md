  Bundles 7 and 8 remain open work; nothing here changes that.
- **Register identity:** **OPEN** (see the header block).

## §4 — The governed object: artifact classes and required ledger content

### §4.1 Artifact classes (carried from decision package §5 — required named examples, not a closed list)

The decision package §5 requires the ledger to record or derive *"artifact
class, **such as** authority, candidate, accepted standalone package, closure
record, working map, historical record, or implementation artifact."* The
governing wording is **"such as"**: these are **required examples**, not a
complete enumeration of every artifact class that may exist.

`authority` · `candidate` · `accepted standalone package` · `closure record` ·
`working map` · `historical record` · `implementation artifact`.

Mechanically, therefore:

- **The named examples are required coverage.** The ledger must be able to
  classify each of these named classes; none may be dropped, renamed, merged, or
  subdivided by this design, and none is renamed, merged, or subdivided here.
- **The list is not closed and is not declared closed here.** Other real
  authority-bearing record types may exist or may later be recognised; this
  design does not exclude them and does not pretend the seven names exhaust the
  world.
- **No class is invented here either.** Naming an additional class is not this
  design's decision; it belongs to the proper later authority and process (§19
  item 12).
- **An artifact the named examples do not cover is recorded truthfully as
  such** — as a recorded state carrying the artifact's own evidence, in the same
  way an unproven status is recorded as unproven (§8). It is **never forced into
  a named class to make it fit, never given an invented class name, and never
  silently reclassified.** Class is assigned from recorded evidence only, never
  from folder placement (§4.2 row 4, §8).
- **Class is not a gate.** Enumeration follows the recorded authority order and
  status derivation follows §8; neither depends on an artifact carrying one of
  the named class names, so an unclassified-under-the-named-examples artifact is
  neither promoted nor discarded by that fact alone.

### §4.2 Required recorded-or-derivable content

The ledger must record **or be able to derive** at minimum the following. These
are **content requirements**, not field names: the decision package §37 leaves
*"exact schemas or field names"* open, so no field name, no key, no value form,
and no vocabulary token is fixed here.

| # | Required content | Mechanical note (design level) |
|---|---|---|
| 1 | Exact filename and controlled path | The logical controlled filename governs; platform upload suffixes are display artifacts, not versions, and are recorded as located-as wording only. |
| 2 | Exact content identity or hash | Recomputed, never remembered (§7). |
| 3 | Version and lineage | Predecessor/successor chain preserved; every prior version remains a preserved entry, never replaced by its successor. |
| 4 | Artifact class | From §4.1's named examples where one applies, assigned from recorded evidence and never from folder placement alone; never forced, never invented; where no named example applies, that fact is recorded truthfully and the taxonomy stays open. |
| 5 | Current status | Derived only under §8. |
| 6 | Governing authority above it | The recorded authority order applying to that artifact; carried, never invented. |
| 7 | Explicit supersession or replacement relationships | Recorded only where a source states them; absence is recorded as absence, never inferred from version numbering. |
| 8 | The acceptance, adoption, or closure evidence that changed its status | The specific record and its identity; a status with no evidence is an unproven status (§8, §14). |
| 9 | Dependency relationships | As stated by the artifacts themselves; not extended by similarity or adjacency. |
| 10 | Scope of authority or accepted effect | Carried verbatim in substance from the artifact's own scope wording; never widened. |
| 11 | Whether the artifact may currently be read, modified, integrated, implemented, or only preserved | **Surfaced as recorded state, never enforced as a gate** (§18). |
| 12 | The repository or local snapshot against which the status was verified | The snapshot the verification actually ran against; the exact mechanism is open (§19). |
| 13 | Contradictions, missing evidence, or unresolved authority state | Preserved and surfaced with the conflicting evidence intact; never resolved, ranked, or silently repaired. |

### §4.3 Ledger character

Ledger entries are **append-only canonical machine-state records**. An entry is
never edited in place; a changed fact is a new appended entry referencing its
predecessor. Ledger entries are machine facts about artifacts — they are **not**
operational logs (§16) and never become an additional evidential vote for
anything they describe (Master §0B *no double evidence*).

## §5 — Identities

All labels below are **[proposed working labels]** used so this design can be
read and audited. They are **not controlled identifiers**, and the exact names
remain open (decision package §37).

- **`artifact_entry_identity`** [proposed] — one canonical entry lineage per
  *logical controlled artifact* (the controlled filename + its version), not per
  physical copy or upload. Establishment converges: two verifications of the
  same logical artifact reach the same entry lineage.
- **`verification_question_identity`** [proposed] — **the stable
  declaration-family lookup key, and nothing more**, deterministic from **{the
  declared operation class, the declared artifact scope} and nothing else**. The
  recorded authority order in force and the derivation-ruleset version in force
  are **not** inputs to this key. They are **generation-varying** inputs of
  `verification_generation_identity` below, so that a change to either produces a
  **successor generation inside this same unchanged family** rather than a
  different family key whose predecessor could no longer be located. This is the
  key AIC-0 establishes or finds in order to **locate any open generation of that
  declaration and any prior committed outcome** (§9). Because it is derived from
  the declaration alone and is therefore **content-blind**, a declaration family
  may hold **successive verification generations** — one per sealed set of
  current inputs — so this key **carries no lifetime one-outcome constraint**,
  closes nothing, locks nothing, and is **not** the source-operation identity
  accepted B9's retry group binds to. The caller's own identity is carried by
  reference only (below) and is **not** part of it, so two callers asking the
  same question reach the same family key — and, because this key is also the
  **family component of the shared pre-generation establishment identity below**,
  two callers asking the same question against the same fresh-establishment
  condition reach the same **one** pre-generation establishment operation as well
  (§9 AIC-0).
- **`establishment_episode_anchor`** [proposed working label — introduced in
  v1_7 because the correction mechanically requires it, and a **proposed label
  only**, because exact schemas, field names, and controlled IDs are already open
  (§19 item 3); **no controlled component ID and no Register ID is assigned to
  it**] — **the deterministic reference to the committed state that caused one
  fresh AIC-1/AIC-2 establishment episode to be open for a declaration family.**
  It names the *cause* of a fresh establishment, never a clock: **no time window,
  timeout, expiry, refresh interval, staleness duration, random nonce, arbitrary
  identifier policy, cache duration, or policy value is invented here or anywhere
  else in this design** (§6.1, §18, §19 item 16). An anchor is resolved at AIC-0
  from **committed, append-only state and from nothing else**, and is exactly one
  of:
  - **(a) the initial no-prior-work family state** — the family key holds no
    committed generation, no committed outcome, and no established
    input-establishment episode. The anchor is deterministic from {the
    `verification_question_identity`, that recorded no-prior-work family state},
    so **every request observing that same committed family state derives the
    same anchor**, with no race to resolve and nothing to invent.
  - **(b) the exact committed reuse-refusal / changed-observation record that
    requires a fresh establishment** — the record a completed current-input
    re-proof appends when it refuses reuse (§6.1, §6.3), or a completed
    unchanged-input confirmation appends when it finds a changed canonical
    generation input (§11), carrying the predecessor generation reference and the
    changed observation. **That record is itself one compare-and-commit**, keyed
    by {the family key, the predecessor generation identity, the recomputed
    changed-input observation it records}: concurrent equivalent re-proofs or
    confirmations that observe the **same** change converge on the **one**
    committed record — the winner commits it, and every loser **re-reads and
    adopts the committed record instead of appending a second one** — so the
    anchor, and therefore the episode it opens, is single.
  - **(c) another already-authorized durable continuation state under which the
    accepted B9 mechanics require the same source operation to remain open** — an
    establishment episode still **open and incomplete** with its recorded
    retryable technical failure keeps **its own** anchor, because accepted B9's
    technical retry serves a source operation only while that original operation
    remains open and incomplete (accepted B9 §1, §7). A request arriving against
    that condition resolves to that same anchor and **attaches**; it never mints a
    second one, and the failed episode's work is never performed twice.

  **An anchor is spent by its own episode and is never silently reused.** A
  **sealed** episode's anchor opens nothing further: the generation exists, and a
  later request is a later request — subject in full to the §6.1 / §6.3
  current-input re-proof before anything committed may be released to it, so **no
  stale basis becomes reusable merely because two callers share an identity**. An
  episode that accepted B9's bounded episode left **exhausted or stopped early**
  likewise yields no fresh anchor of its own: nothing is sealed, nothing is
  committed, the request stays **unresolved**, and continuation under that same
  identity is accepted B9's own real-change path under its accepted rules — never
  a fresh episode minted here to walk around admission (§11, §12 rows 20 and 23,
  §14). **A failed or exhausted episode therefore never becomes authority, never
  becomes a refusal, and never locks the content-blind family key**, while a
  genuinely changed world always commits a new anchor record under (b) and opens
  one new shared episode of its own.
- **`verification_input_establishment_identity`** [proposed] — **this component's
  canonical source-operation duplicate-prevention identity for the work that
  happens before a generation exists, and — corrected in v1_7 — deliberately
  caller-blind**: the identity of **one shared fresh AIC-1/AIC-2 establishment
  episode** in which a generation's input basis is assembled and sealed. It is
  deterministic from {the `verification_question_identity` — the stable
  declaration family {declared operation class, declared artifact scope}; the
  `establishment_episode_anchor` resolved for this episode; the exact
  **authority-order source reference to consult**; the exact
  **derivation-ruleset source reference to consult**; the input-establishment
  operation class and version}. **No caller's own identity is an input to it**:
  `caller_declaration_identity` (below) is a caller-owned reference only, so
  **two callers asking the same authority question against the same
  fresh-establishment condition derive the same identity, resolve to the same
  claim, and are served by the same one operation.** It is **resolved and
  committed at AIC-0, before the first enumeration step and before the first
  content read**, and stays **unchanged across every attempt of that source
  operation** (§9 AIC-0, AIC-1, AIC-2).
  - **Its canonical inputs are the declaration family, the anchor, and those
    exact source references — nothing else.** The membership, the determinate
    absences, the status-evidence records, and the bytes observed **from** those
    references are this operation's **output**, never its canonical inputs; they
    become generation inputs only when a complete validated basis is sealed. A
    change to a pre-generation canonical input creates a **new
    input-establishment identity and a new retry group**; an observed change in a
    file's content is captured in the basis this operation produces and is
    **never silently substituted inside an already established generation**
    (accepted values package §10).
  - **Its duplicate fence is the `input_establishment_claim`** [proposed]: an
    append-only, **one compare-and-commit** claim keyed by
    `verification_input_establishment_identity`. **At most one live source
    attempt may hold the claim**, and **at most one completed sealed basis may
    commit** for that identity. **The compare-and-commit winner establishes the
    shared open operation and is the one executing run of that episode; the loser
    does not fail and does not open a second operation — it re-reads the
    committed family and open-operation state and attaches to the same
    operation** (below). A duplicate attempt arriving after the seal **finds and
    absorbs the committed basis** rather than producing a second one; a crash or a
    technical stop **releases or recoverably supersedes** the live claim
    **without inventing a basis**, and because every input of this identity is
    committed state, a re-derivation after a crash lands on the **same** identity
    and finds whatever was committed rather than creating a second shared
    operation (§9 AIC-1, AIC-2; §12 rows 18, 23, 24).
  - **Per-caller attachment — `establishment_caller_attachment`** [proposed
    working label — introduced in v1_7, mechanically necessary, **proposed
    only**, and carrying no controlled component ID and no Register ID]:
    append-once per {this shared identity, that caller's
    `caller_declaration_identity`}. **Caller identities are preserved as separate
    references on the one shared operation and are never merged, rewritten, or
    discarded**; each attached caller keeps its own request reference and its own
    operational log evidence (§16) and receives its own release. An attachment
    creates **no** second operation, **no** second claim, **no** second
    AIC-1/AIC-2 execution, **no** second retry group, and **no** evidential
    weight of any kind about any artifact (Master §0B *no double evidence*).
  - **Its retry group is one accepted-B9 group**, derived from {this identity,
    the input-establishment operation class} — accepted B9 §4's one group per
    source-operation duplicate-prevention identity — and, because the identity is
    caller-blind, **identical concurrent work has exactly one such group and no
    caller-specific duplicate group can exist**. The **original execution is the
    initial episode's ordinal 1 by reference**, exactly as the accepted
    retry-values wiring records it. After a durable technical failure, every
    re-attempt requires **accepted B9's R1 admission**, the **exact accepted
    `retry_budget_ref`**, the **recorded schedule class with no default**, and
    proof that **no live attempt exists for the group**; R2 then **reacquires the
    source claim** and re-executes **only the AIC-1/AIC-2 input-establishment
    seam** under this same canonical identity (§11).
  - **It is episode-scoped and carries no outcome lock.** Its fence is a *basis*
    fence — one sealed basis at most for that episode — never an outcome fence:
    an outcome commits only under `verification_generation_identity` (§9 AIC-4).
    Because the anchor changes when a fresh establishment condition changes, a
    new episode is a new identity with a new claim and a new group, so nothing
    here gives the content-blind declaration family a lifetime lock of any kind.
  - A technical failure at AIC-1 or AIC-2 is **recorded against this identity**
    and supplies accepted B9's durable `technical_retryable` evidence, while
    committing **no generation, no snapshot, and no refusal** (§6.2 (b)). It is
    **one** record set, **one** open operation, and **one** retry group for that
    episode however many callers are attached to it.
- **`verification_generation_identity`** [proposed] — **this component's
  source-operation duplicate-prevention identity for an established
  generation**: the canonical identity of **one sealed current-input generation**
  of a declaration family, deterministic from {the
  `verification_question_identity`; the exact **recorded authority-order identity
  and version in force**; the exact **derivation-ruleset version in force**; the
  exact **completed** enumerated membership as sealed by the AIC-1/AIC-2 basis
  transaction; the identity of **every** enumerated artifact; **every**
  revalidated recomputed content identity, or the recorded
  **determinate-absence identity** where an enumerated member is determinately
  absent; **every status-evidence record** on which any status derivation
  depends, by identity}. The same sealed basis converges on the same generation
  identity; **any** change of the recorded authority order, of the ruleset
  version, of membership, of an enumerated artifact, of a content identity, of a
  recorded determinate absence, or of a cited evidence record produces a
  **different** generation identity, recorded as a **new generation linked to its
  predecessor in the same unchanged declaration family**. This is the identity
  under which **at most one outcome may ever commit** (§9 AIC-4) and — being this
  component's duplicate-prevention identity for an established generation — it is
  the **source-seam canonical identity** that accepted B9's retry group binds to
  when a technical failure **of an established generation** is retried (accepted
  B9 §4, §5 R2, §6; §11 below). **It comes into existence only when the
  AIC-1/AIC-2 basis-establishment transaction has fully revalidated its tentative
  basis from the actual sources and atomically committed that basis as sealed**,
  and it is derived from **that sealed basis alone**: no re-proof, no
  declaration, and no partial or unrevalidated read ever establishes, preassigns,
  or reserves one (§6.1, §6.3, §9 AIC-0, AIC-1, AIC-2).
  - **The source seam bound to this identity is the post-seal
    outcome-completion seam AIC-3 through AIC-5** — status derivation,
    contradiction detection, the single outcome commit, and the terminal and
    release. An **initial** execution reaches this seam only after AIC-1/AIC-2 has
    sealed the basis and derived the generation identity from it.
  - **A B9-admitted established-generation re-attempt is a new
    `verification_run_identity` bound directly to this already-existing
    generation.** It **enters at AIC-3** and derives status, detects
    contradictions, attempts the AIC-4 outcome commit, and performs AIC-5 **using
    only that generation's previously committed sealed basis**. It performs no
    enumeration, no live-source identity verification, no basis revalidation, no
    seal or reseal, no basis replacement, and no re-derivation of a generation
    identity. **AIC-1 and AIC-2 remain exclusively the pre-generation
    input-establishment seam** and are never executed or re-executed under an
    existing `verification_generation_identity` (§9, §11).
- **`verification_run_identity`** [proposed] — one identity per **execution** of
  the check: the parent operation of {enumerate → verify identity → derive status
  → detect contradiction → commit outcome}, with a child operation identity per
  separately executed step. This reuses the accepted parent/child
  operation-identity pattern already carried by the accepted packages; it does
  not redefine it. **Every execution whose basis-establishment transaction seals
  a basis is bound to exactly one `verification_generation_identity`** and never
  to a second one: several executions may attempt one open generation, while the declaration
  family may hold several generations in chronological order, each with its own
  single outcome. Two kinds of execution therefore exist, and they are
  mechanically different:
  - **The initial execution** is the run that **wins and holds the
    `input_establishment_claim`** for the shared
    `verification_input_establishment_identity` resolved and committed at AIC-0,
    and is bound, after the seal, to the generation derived from that sealed
    basis. It alone runs AIC-1 and AIC-2 **for that episode**. **Every other
    request that resolves to the same identity attaches to that same episode**
    under its own `establishment_caller_attachment`, performs no second
    AIC-1/AIC-2 of its own, and converges on whatever that one shared episode
    produces (§9 AIC-0).
  - **An established-generation retry execution** is a **new run bound directly
    to the already-existing `verification_generation_identity`** — a new parent
    operation on this component's own post-seal boundaries, exactly as accepted
    B9 R2 requires of a seam — and never a second identity for that generation
    and never a second committed outcome for it (§9, §11). It **enters at AIC-3**
    and runs AIC-3 through AIC-5 on that generation's committed sealed basis. It
    **must not** create or bind a new `verification_input_establishment_identity`,
    acquire an `input_establishment_claim`, execute AIC-0, AIC-1, or AIC-2,
    enumerate artifacts, recompute artifact identities, perform basis
    revalidation, seal or reseal a basis, derive another generation identity, or
    replace any generation input.

  An execution that fails technically **before** its
  basis is sealed is bound to **no** generation at all — it commits no generation
  outcome and places no constraint on the declaration family — but it is **not**
  unbound: it executes under the shared
  `verification_input_establishment_identity` resolved and committed at AIC-0,
  holds that identity's `input_establishment_claim`, and its durable technical
  failure is recorded against that identity and served by that identity's **one**
  accepted-B9 retry group — one group for that episode, however many callers are
  attached to it (§6.2 (b), §11).
- **`authority_snapshot_identity`** [proposed] — deterministic from {the
  enumerated governing set, the verified content identities of every member of
  that set, the derivation-ruleset version in force}. Identical verified inputs
  converge on the same snapshot identity; any difference in any member's content
  identity produces a different snapshot. Because status is derived from these
  same recorded inputs under that ruleset version, **every artifact whose content
  the run relied on — each governing member and each evidence record cited in any
  status derivation — is part of the enumerated input set and therefore part of
  this identity** (§6, §9 AIC-1).
- **`refusal_basis_identity`** [proposed] — the same kind of deterministic input
  identity for a **deterministic authority refusal** as `authority_snapshot_identity`
  is for a proven governing set, and the **only** valid current-input proof basis
  for reusing a refusal (§6.3). It is deterministic from {the declared operation
  class and declared artifact scope, the recorded authority order in force, the
  derivation-ruleset version in force, the completed enumeration as committed at
  AIC-1, the recomputed content identity of every enumerated member the refusal's
  condition depends on — including every evidence record cited in the status
  derivations that produced it, and including any member recorded as
  **determinately absent**, whose determinate absence is itself the recorded
  input — and the exact recorded unproven condition with the members and records
  it names}. A refusal is **basis-complete** only where every input its condition
  depends on was actually read and identified, or determinately established as
  absent, by that run. A refusal that is not basis-complete has no
  `refusal_basis_identity` and is **never reusable** (§6.3, §14).
- **`technical_failure_record_identity`** [proposed] — one durable technical
  failure record per {run, failing step}, carrying the exact technical condition,
  the step it occurred in, and the recorded mark that it is technical and
  potentially retryable — the marking pattern accepted B9 §3 already consumes
  from a source operation, and this seam's durable **`technical_retryable`**
  outcome for B9's classification (§11.1). Where the failure occurred **before** a basis was
  sealed, the record names the `verification_input_establishment_identity` it
  belongs to; where it occurred **inside an established generation**, it names
  that `verification_generation_identity`. It is a record of a failed
  **attempt**, never an outcome of a generation and never an outcome of the
  declaration family: it commits no snapshot and no refusal, and nothing may ever
  be reused from it as authority or as a decided refusal (§6.2, §11, §14).
- **`input_reproof_identity`** [proposed] — one identity per current-input
  re-proof: the bounded child operation that, at reuse time, re-enumerates under
  the same declared scope and authority order, recomputes each recorded input's
  content identity from the actual files, and recomputes the resulting identity
  for comparison — **the `authority_snapshot_identity` when a committed snapshot
  is the candidate for reuse (§6.1), or the `refusal_basis_identity` when a
  committed deterministic refusal is (§6.3)**. It is a read and recompute
  operation only; it commits no snapshot and no refusal of its own, and it
  **establishes, preassigns, and reserves no `verification_generation_identity`**:
  where it proves that a canonical input changed, it refuses reuse and
  **commits — under the one compare-and-commit of the
  `establishment_episode_anchor` case (b) above — the reuse-refusal record
  carrying the predecessor reference and the changed observation**, which is then
  the anchor of the **one** fresh shared
  `verification_input_establishment_identity` episode the request is handed to; a
  concurrent equivalent re-proof observing the same change **adopts that same
  committed record** instead of appending a second one, so both reach that same
  one episode (§6.1, §6.3, §9 AIC-0). It is itself subject to §6.2: a read that
  fails during a re-proof is a technical failure, never a proof of anything.
- **`refusal_record_identity`** [proposed] — one identity per deterministic
  authority refusal outcome, carrying the exact unproven condition and, where the
  refusal is basis-complete, its `refusal_basis_identity`. It is this seam's
  durable **`terminal_substantive`** outcome for accepted B9 — **routing
  terminology only, never a meaning judgment** — and it carries no
  substantive-retry policy or authorization reference, so no same-group machine
  re-execution of it exists (§11.1).
- **`caller_declaration_identity`** [proposed] — the requesting operation's own
  identity together with the operation class it declares, **carried by reference
  only.** The **declaration** it makes — {declared operation class, declared
  artifact scope} — is what the family key is derived from; **the caller's own
  operation identity is an input to no shared duplicate-prevention identity of
  this component.** It is not part of `verification_question_identity`, and —
  corrected in v1_7 — it is **not** part of
  `verification_input_establishment_identity` either, so a caller's identity can
  never force a second pre-generation establishment operation for work another
  caller is already performing, and can never split identical concurrent work
  into two accepted-B9 retry groups. The control plane never adopts, replaces,
  re-issues, **merges, or discards** a caller's identity: every caller attached to
  one shared episode stays **separately referenced** by its own
  `establishment_caller_attachment` and its own operational log evidence, and
  receives its own release (§9 AIC-0, §10, §16).

**Snapshot immutability.** An authority snapshot is an immutable derived record.
It is never amended. A changed world produces a **new** snapshot, never an edit
to an existing one.

**Refusal immutability.** A refusal record is likewise immutable. It is never
amended, never re-dated, never upgraded into a pass, and never rewritten when the
world changes; a changed world produces a **new** run with its own outcome.

## §6 — The deterministic pre-operation check

The decision package §5 settles exactly two permitted outcomes. This design adds
no third.

**Outcome A — proven:** return the **verified governing set** and an **authority
snapshot reference**.

**Outcome B — not proven:** **stop** and report that authority cannot be proven
safely, naming the exact unproven condition.

There is no partial pass, no "best available" governing set, no degraded
snapshot, no majority rule, and no provisional authority (§13).

**Stages (design level):**

1. **Declare** — the caller declares its operation class and the artifact scope
   it intends to act upon. Read-only towards every governed artifact: no artifact
   is written, and none is read for content here. The declaration resolves the
   stable family key, then the `establishment_episode_anchor` from committed
   state, and from those the **shared, caller-blind**
   `verification_input_establishment_identity`; the only things committed are that
   identity's own append-only records — its one-compare-and-commit
   `input_establishment_claim` where this request wins it, or this caller's
   `establishment_caller_attachment` to the episode that already holds it — both
   established **before** the first enumeration step and before the first content
   read (§5, §9 AIC-0). **Two callers declaring the same question against the
   same fresh-establishment condition resolve to the same identity and therefore
   to one shared operation, and only one of them performs the work.** **No
   generation identity is established, preassigned, or reserved at this stage.**
2. **Enumerate** — assemble the governing set required for that class: the
   authority order in force, plus the current Design and Wiring Map, plus the
   accepted packages and records that bear on the declared scope within their
   own stated scope. **Every artifact whose content the run will rely on is
   enumerated, including each record that will be cited as status evidence**, so
   that nothing the outcome depends on sits outside the recorded input set.
   Enumeration follows the recorded authority order; it never ranks, selects, or
   promotes. It runs **under the shared
   `verification_input_establishment_identity` resolved and committed at stage 1
   and under that identity's `input_establishment_claim`, once for that
   establishment episode and never once per attached caller** (§5, §9 AIC-0). An enumeration that cannot be completed is classified under
   §6.2 before anything else happens with it: **determinate absence of a required
   governing record** ends the run at a deterministic Outcome-B refusal naming it;
   an enumeration step that **could not be performed** (a read that failed) is a
   technical failure state recorded against that input-establishment identity and
   commits no outcome at all.
3. **Verify identity** — recompute each member's content identity and compare it
   with the recorded identity (§7). A **mismatch** and a **determinately absent**
   member each end the run at a deterministic Outcome-B refusal naming that
   member. A member that **cannot be read at that moment**, or whose identity
   cannot be recomputed because the read or the recomputation itself failed, is a
   **technical failure state** under §6.2: the run stops without proving
   authority, the caller receives an Outcome-B stop naming the technical
   condition, and **no refusal is committed**. **Stages 2 and 3 are one
   basis-establishment transaction:** the tentative basis they capture is **fully
   revalidated from the actual sources** and only then **atomically sealed**, and
   the `verification_generation_identity` is derived from that sealed basis alone
   (§9 AIC-1, AIC-2). A revalidation that differs, or that cannot be completed,
   seals nothing, establishes no generation, and is recorded against the
   input-establishment identity as a technical and potentially retryable
   condition.
4. **Derive status** — for every member, derive status only under §8, and **only
   from the sealed basis**: no input is re-read, refreshed, or substituted inside
   an established generation.
5. **Detect contradiction** — record any contradiction, missing evidence, or
   unresolved authority state found **in that same sealed basis**. Any such
   finding ends the run at a deterministic Outcome-B refusal with the conflicting
   evidence preserved intact and unresolved.
6. **Commit outcome** — commit either the snapshot record (Outcome A) or the
   deterministic refusal record (Outcome B) **for the
   `verification_generation_identity` derived from the sealed basis of stages 2
   and 3**, then the single parent terminal log, then release the reference to
   the caller (§9). A run that ended in a technical failure state reaches no
   commit at this stage: it appends its durable technical failure record and
   leaves its **generation** open and unresolved where one was sealed — and where
   the failure prevented that basis from being sealed, leaves no generation and
   no outcome at all, the failure being recorded against the
   `verification_input_establishment_identity` and served by that identity's own
   accepted-B9 retry group (§6.2, §11).

**The snapshot proves what was true at verification time and nothing more.** It
is not a permission, not an approval, not an acceptance, not an adoption, and
not evidence about the substantive correctness of anything it references.

### §6.1 Reuse of an existing snapshot — proven, never assumed

Because a snapshot proves only the verification-time state, an existing snapshot
may not stand in for a new operation's check merely because the caller's
declaration and scope look the same. Master V10's standing lesson and Defaults §0
govern here: *trust disk, never the doc*, and *a claim requires disk evidence,
not remembered state*; the decision package §6 records that this control plane
operationalizes *"actual files over remembered descriptions."* Two cases are
therefore mechanically distinct:

- **Concurrent absorption, inside one open generation — preserved unchanged in
  substance.** Two callers asking the same question while that same run's
  verification is open converge on that one run **only where they resolve to the
  same open `verification_generation_identity`** — that is, against the identity
  checks that run has already performed, over the same sealed current inputs:
  exactly one outcome commits **for that generation** and the other observes it
  (§9 AIC-4). No second verification of record occurs, and no stale state can
  arise, because the disk reads backing the outcome   belong to that same open generation. **Before any basis is sealed**, the same
  convergence is provided one level earlier, by the **shared, caller-blind**
  `verification_input_establishment_identity` and its `input_establishment_claim`
  (§5): two identical concurrent requests — the same declaration family, the same
  `establishment_episode_anchor`, the same authority-order and derivation-ruleset
  source references, the same operation class and version — **derive the same
  identity**; exactly one of them wins the claim and becomes the executing run,
  and the other **re-reads the committed family and open-operation state and
  attaches** to that same operation rather than opening a second one. **The
  AIC-1/AIC-2 enumeration, live-source identity checking, revalidation, and
  basis establishment are therefore performed once for that shared episode, not
  once per caller**, exactly one accepted-B9 retry group serves any pre-seal
  technical failure of it, and a duplicate attempt arriving after the seal finds
  and absorbs that identity's committed sealed basis rather than producing a
  second one (§9 AIC-0…AIC-2, §10). Both callers remain **separately referenced**
  throughout, and both converge on the resulting
  `verification_generation_identity` and its one-outcome fence if the basis seals.
  A request that resolves to a **different** fresh-establishment condition, or to
  different canonical inputs, is **not** absorbed: it takes its own
  input-establishment operation of record, and whatever successor generation that
  operation's sealed basis defines.
- **Reuse across runs — permitted only on fresh proof.** A request that arrives
  after a run's outcome has committed is a **new** question about the **current**
  world. A committed snapshot may be returned to it only when a **current-input
  re-proof** (§5 `input_reproof_identity`) completes and proves all of the
  following at that moment:
  1. re-enumeration under the same declared scope, operation class, and recorded
     authority order produces the **same membership** as the snapshot's recorded
     enumerated input set — no member added, removed, or replaced;
  2. every member's content identity, **recomputed from the actual file now**,
     equals the identity recorded in that snapshot (§7);
  3. the derivation-ruleset version in force is the same version the snapshot
     names;
  4. the recomputed `authority_snapshot_identity` is therefore **identical** to
     the committed one.

  If all four hold, the current inputs are the **same generation**: the existing
  snapshot is returned with the re-proof recorded as its own operational evidence
  (§16); **no second snapshot is committed and no snapshot is amended.** If any of
  them fails to hold, the stored snapshot is **not** returned. The completed
  re-proof then does exactly three things and nothing more: it **refuses reuse**,
  it **commits — under one compare-and-commit — the reuse-refusal record carrying
  the predecessor generation reference and the changed observation**, and it
  **opens exactly ONE fresh shared `verification_input_establishment_identity`
  episode anchored on that committed record** for the current world; a concurrent
  equivalent re-proof observing the same change **adopts that same committed
  anchor record** and reaches that same one episode rather than opening a second
  (§5).
  **It establishes, preassigns, reserves, and executes under no
  `verification_generation_identity` of its own.** A successor generation exists
  only if and when that fresh operation's AIC-1/AIC-2 basis transaction fully
  revalidates and atomically seals a complete basis; the successor is then linked
  to the predecessor this re-proof located, and its run either commits **its own**
  new snapshot for the new world or reaches **its own** Outcome B. The earlier
  generation's committed outcome is neither reused nor amended, and it **never
  prevents a successor generation from committing** its own outcome.

  If the re-proof itself cannot be completed, the stored snapshot is **not**
  returned and **there is no fallback to it** (§14), and the condition is
  classified under §6.2 like any other: a member that is **determinately absent
  now**, or a ruleset version that is **determinately unestablishable from
  readable evidence**, ends reuse and hands the request to a fresh
  input-establishment operation, whose sealed basis records that determinate
  condition and whose run commits the deterministic Outcome-B refusal naming it;
  a member that **cannot be read at that moment**, or a re-proof step that fails
  technically, is a **technical failure state** that commits no outcome, seals no
  basis, establishes no generation, is recorded against the input-establishment
  identity, and leaves the request unresolved (§6.2, §11, §12 row 17).

**No expiry value, refresh interval, or staleness window is invented here.**
Freshness is proven by identity, not by elapsed time; whether any time-based
validity window or scheduled re-verification ever exists remains open (§17.3,
§19 items 8 and 16). Equally, this design does not extend proof beyond the moment
of proof: the interval between a released snapshot and the caller's own action
belongs to the caller's operation boundary, which is the Unified Durable
Operation Kernel's open and blocked edge (§17.13, §19 item 17), and nothing here
decides or anticipates it.

### §6.2 Two kinds of stop: a deterministic authority refusal and a technical failure state

**This is a distinction of recorded machine state behind a stop, not a third
outcome.** In every stop the caller receives Outcome B exactly as the decision
package §5 settles it: the check stops and reports that authority cannot be
proven safely, naming the exact condition, and no snapshot exists. What differs
is **what the run commits, what stays open, and what may ever be reused** —
which is mechanical routing, never a judgment about meaning, exactly as accepted
B9 §3 characterises outcome classification.

**(a) Deterministic authority refusal — a determinate statement about the
evidence as read.** The run performed the reads it needed and the evidence
itself does not prove authority:

- a recomputed content identity that disagrees with the recorded identity;
- a governing member **determinately absent** from where the recorded authority
  order names it, established by a completed lookup;
- a status whose admissible evidence (§8) is **determinately missing**;
- two records that determinately contradict about one artifact identity;
- only inadmissible proof exists (placement, wording, summary, absence of a
  contrary record);
- an enumeration that cannot be completed because a required governing record is
  determinately absent;
- a derivation-ruleset version that readable evidence determinately fails to
  establish.

This is committed at AIC-4 as **that generation's one** outcome — the one outcome
for the frozen current inputs it was derived over, never a lifetime outcome for
the declaration family — with the conflicting or missing evidence preserved
intact. It is this seam's durable **`terminal_substantive`** outcome for accepted
B9, which is **routing terminology only** and never a meaning judgment: it says
the refusal is not a technical failure and is therefore not machine-retryable
under a technical budget, and because this seam supplies no adopted
substantive-retry policy reference and no per-case substantive-retry
authorization, B9's R1 fails closed on that route (§11.1). It is **not** a technical
failure and is **never** admitted as one, never retried into a pass, and never
made true by repetition: repeating the check against the same evidence derives
the same refusal, because derivation is deterministic over the same inputs (§8,
§11). Where such a refusal is basis-complete it carries a `refusal_basis_identity`
and may be reused only under §6.3.

**(b) Technical failure state — the run could not perform a step at that
moment.** A member that cannot be read now; a content identity that cannot be
recomputed because the read or the recomputation failed; a step interrupted; an
unavailable snapshot service (this component's own record service); a step
timeout; and a **full revalidation of the tentative input basis that differs from
what was first observed, or that cannot be completed** —
`input_basis_changed_during_establishment`, or the exact failed-revalidation
condition (§9 AIC-1, AIC-2). Mechanically:

- the run appends its **durable technical failure record** (§5
  `technical_failure_record_identity`) naming the exact condition and the step,
  **marked technical and potentially retryable** — which is this seam's durable
  **`technical_retryable`** outcome for accepted B9 §3, and the marking B9
  already consumes from a source operation for that class (§11.1) — recorded **against the `verification_input_establishment_identity` where no
  basis had yet been sealed**, and against the `verification_generation_identity`
  where one had;
- **no outcome is committed** — no snapshot, and **no refusal record.** AIC-4 is
  not reached;
- where the generation input basis had already been sealed, the
  **generation remains open and unresolved** under its
  `verification_generation_identity`, in exactly the settled shape accepted B9 §1
  and §7 describe for a handled retryable technical failure (the source operation
  stays open and incomplete with a recorded retryable failure; it is never
  auto-treated as anything else, and B9's technical retry serves it only while
  the original operation remains open and incomplete);
- because nothing was committed, **there is nothing for a later request to be
  absorbed against**: a later request for the same question is absorbed into that
  still-open generation **only where it resolves to the same generation
  identity** (§6.1, §9 AIC-0), and — before any basis is sealed — into that
  still-live input-establishment operation through the **shared, caller-blind**
  identity it resolves to and that identity's `input_establishment_claim`, which
  absorbs a duplicate attempt against the committed sealed basis where one exists
  and otherwise **attaches** the request to that same live operation — never a
  second live attempt, and never a second operation for the same
  fresh-establishment condition; a request that resolves to neither begins a new
  run of record under the input-establishment identity its own
  fresh-establishment condition resolves to; it is never answered with a refusal,
  and never with a snapshot;
- the caller is told, in that Outcome-B stop, that the condition is technical and
  that authority is unproven — never that authority was determinately refused.

**A technical failure before the basis is sealed commits no outcome — and is
still fully owned here.** Where the failing read, recomputation, or revalidation
is precisely what prevents the generation input basis — and therefore the
`verification_generation_identity` — from being sealed, the run records the
technical failure **against the shared `verification_input_establishment_identity`
that AIC-0 resolved and committed for this establishment episode** (§5), naming
the executing run and the exact failing step — **one record set, one open
operation, and one retry group for that episode however many callers are attached
to it.** **No snapshot, no refusal, no generation outcome, and no content-blind
lifetime lock is committed**, AIC-4 is not reached (§9 AIC-1, AIC-2), and the
content-blind declaration-family key acquires no constraint of any kind. What
**does** bind is this component's own pre-generation source seam:

- that durable record **is** accepted B9's `technical_retryable` evidence for the
  input-establishment operation, and it commits no generation, no snapshot, and
  no refusal (accepted B9 §3);
- the operation's **one** accepted-B9 retry group is derived from {the
  `verification_input_establishment_identity`, the input-establishment operation
  class}, with the original execution recorded as the initial episode's **ordinal
  1 by reference** (accepted B9 §4; accepted values package §5) — and, because
  that identity is caller-blind, **identical concurrent work has exactly one such
  group, and no caller-specific duplicate group can exist**;
- a re-attempt requires accepted B9's **R1 admission**, the **exact accepted
  `retry_budget_ref`**, the **recorded schedule class with no default**, and
  **proof that no live attempt exists for the group**; R2 then reacquires the
  `input_establishment_claim` and re-executes **only the AIC-1/AIC-2
  input-establishment seam** under that same canonical identity (§11);
- the crash or technical stop **releases or recoverably supersedes** the live
  claim **without inventing a basis**, and recovery is lookup-first over the
  append-only records of what that attempt actually completed (§12 row 18).

**Nothing on this pre-generation path is delegated to an unnamed seam, deferred
to an unspecified child contract, or left open here.** The identity, the
duplicate fence, the retry group, the budget binding, the schedule class, the
one-live-attempt rule, and the recovery behaviour are all stated above. What
remains accepted B9's is what was always B9's: admission, attempt counting,
disposition, and classification (§11, §19 item 18).

**Restored readability is therefore mechanically distinguishable from unchanged
evidence, and the two can never be confused:**

- a technical failure leaves **no committed refusal**, so a later attempt or
  request derives whatever the world then proves — Outcome A if everything
  verifies, Outcome B if it does not — and nothing carries the earlier failure
  forward as a decision. **Which path that later attempt takes depends on whether
  a basis had sealed, and the two are never interchangeable:**
  - **Before any basis has sealed**, an admitted retry may **re-read and
    revalidate the actual sources**, and it does so **only** through the same
    pre-generation input-establishment operation's **AIC-1/AIC-2 seam**, under
    the same shared `verification_input_establishment_identity` and its
    reacquired claim, once for that episode and for every caller attached to it. Restored readability is proved there, in that seam, and a basis seals
    only if the full revalidation matches (§9 AIC-1, AIC-2).
  - **After a basis has sealed**, an admitted retry performs **no re-read and no
    revalidation at all**: it continues at **AIC-3** on that generation's
    immutable sealed basis, because the generation's inputs are fixed and a live
    source is never consulted inside it. A member that has changed on disk does
    not enter that run; it is handled only by a later completed canonical-input
    confirmation or reuse re-proof, which refuses the old generation and starts a
    **fresh input-establishment operation** whose seal defines the successor
    generation (§6.1, §6.3, §11).

  In both cases the earlier technical failure record stays preserved as attempt
  history and is never re-read as a decision;
- a deterministic refusal may be reused **only** on a completed re-proof that
  recomputes every one of its basis inputs **from the actual files now** and
  reaches the identical `refusal_basis_identity` (§6.3) — which a refusal caused
  by a failed read could never satisfy, and which no longer arises, because a
  failed read no longer produces a refusal at all.

**(c) Unresolved — neither established.** Where the run's own recorded evidence
does not establish which of (a) and (b) a condition is, the run records the
condition as **unresolved**: no outcome is committed, nothing is reusable, and
resolution is recovery-first. This is not a permitted outcome and never becomes
one; it is the honest recorded state of a run that reached no outcome. It is
appended as the durable terminal evidence **`indeterminate_recovery_required`** —
accepted B9 §3's own vocabulary for the source-side state it classifies as
**`indeterminate`**, consumed here rather than invented — so that B9 classifies
it without guessing (§11.1). That record is **evidence about the run, never a
third outward outcome**: the caller still receives Outcome B exactly as the
decision package §5 settles it, and nothing about the two-outcome rule changes.
Under accepted B9's own rules an `indeterminate` state is **never retried,
recovery-first and fail-closed** — no admission until this seam's own recovery
resolves the state — and this design admits no retry of its own in that state
(§11, §11.1, §14). The platform-level means by which a failed read is told apart from
a determinate absence is not settled by any source read here and is not chosen
here (§19 items 4 and 18, §20 item 8).

**No condition ever changes class by repetition, by waiting, or by exhaustion.**
A technical failure never becomes a refusal because retries ran out; an exhausted
or early-stopped retry episode leaves its generation unresolved and unfinished
with truthful exhaustion recorded, which is what the accepted retry values require
(*"no fake success, no hidden failure"*; stop, say why, keep the work record, and
preserve the unfinished state) — §11.

### §6.3 Reuse of an existing refusal — proven, never assumed

A committed refusal is a statement about the evidence at the moment it was
derived, exactly as a snapshot is. It may be released to a **later** request only
where all of the following hold; otherwise a new run of record proceeds:

1. **It is a deterministic authority refusal (§6.2 (a)).** A technical failure
   state and an unresolved state are never reused, because neither is an outcome
   and neither is committed as one.
2. **It is basis-complete.** Every input its condition depends on was read and
   identified, or determinately established as absent, by the run that produced
   it, and the enumeration behind it was completed (§5
   `refusal_basis_identity`). A refusal without a complete basis is never
   reusable and never absorbs a later request.
3. **A current-input re-proof completes now** (§5 `input_reproof_identity`) and
   proves, at that moment: the same enumeration membership; the same recomputed
   content identity for every basis member, **recomputed from the actual file
   now**; the same determinate absence for every member the basis records as
   absent; and the same derivation-ruleset version in force.
4. **The recomputed `refusal_basis_identity` is identical** to the one the
   refusal carries, and the same unproven condition is therefore re-derived over
   those same inputs under that same ruleset version.

If all four hold, the current inputs are the **same generation**: the recorded
refusal is returned unchanged, with the re-proof recorded as its own operational
evidence (§16); **no second refusal is committed, no refusal is amended or
re-dated, and the unproven condition is not re-litigated by repetition.** If any
of them fails to hold, the stored refusal is **not** returned. The completed
re-proof **refuses reuse**, **commits — under one compare-and-commit — the
reuse-refusal record carrying the predecessor generation reference and the changed
observation**, and **opens exactly ONE fresh shared
`verification_input_establishment_identity` episode anchored on that committed
record**, which a concurrent equivalent re-proof observing the same change joins
rather than duplicating; it establishes,
preassigns, reserves, and executes under **no** `verification_generation_identity`
of its own. A successor generation of the same declaration family, linked to the
predecessor located here, exists only if and when that fresh operation's
AIC-1/AIC-2 basis transaction fully revalidates and atomically seals a complete
basis; its run of record then reaches — and is free to commit — whatever outcome
the current evidence proves. If the re-proof itself cannot be completed, §6.2
governs: a failed read is a technical failure state committing nothing, sealing
no basis and establishing no generation, recorded against the input-establishment
identity, and there is **no fallback to the stored refusal** (§14).

**Reuse never widens.** A refusal proves only its own recorded unproven
condition, for its own generation of its own question. It is never released to a different question, is
never evidence about any artifact's substantive correctness, and never becomes a
reason not to verify — the re-proof is the verification.

## §7 — Content identity and verification method

This is **existing project practice, referenced — not a new invention**:

- the Companion (authority 4) preserves each embedded source after a
  machine-readable marker carrying its **exact byte length and SHA-256**, and
  defines verification as reading exactly that byte length and comparing the
  reconstructed hash against the original;
- the accepted acceptance and closure records in this project record artifact
  identity as **SHA-256 + line count + byte count**, recalculated immediately
  before the record is written, and treat a three-value match as the identity
  proof;
- Master V10's standing lesson and the Defaults §0 both state **trust disk,
  never the doc — including this file**.

**Design rules that follow mechanically:**

- Identity is **recomputed at verification time**, never carried forward from a
  document's own claim about itself, never taken from a model's summary, and
  never inferred from a filename.
- **Reuse of an earlier verification's result is itself an identity claim about
  the present**, and is therefore proven by recomputation at reuse time —
  whether the earlier result was a snapshot (§6.1) or a deterministic refusal
  (§6.3) — never by the age, presence, or convenience of the earlier record.
- A recorded identity and a recomputed identity that disagree is an **integrity
  finding**, never a coin-flip and never silently updated.
- **A failure to compute an identity is not an identity finding.** A read or
  recomputation that could not be performed proves nothing about the artifact and
  is routed as a technical failure state (§6.2 (b)), never recorded as a
  mismatch, an absence, or a refusal.
- The **specific algorithm, value set, canonicalisation, and storage of these
  identities remain open** (§19); what is settled here is that identity is
  recomputed and compared, and that a mismatch fails closed.

## §8 — Status derivation rules

Status is derived **only** from recorded evidence, in this order of admissible
proof:

1. an explicit **acceptance or adoption record** by Ness for that exact artifact
   identity;
2. an explicit **closure record** stating the package status for that exact
   artifact identity;
3. an explicit statement carried by a **higher authority** in the authority
   order about that artifact.

**Never admissible as proof of status:**

- repository or folder placement by itself;
- a filename, a version number, or the word `FINAL`;
- final-sounding wording inside the artifact;
- completeness, internal consistency, or passing an audit;
- a model's summary, recollection, or paraphrase;
- the absence of a contrary record.

**Derivation is deterministic over its recorded inputs.** The same admissible
evidence, recomputed to the same content identities under the same
derivation-ruleset version, yields the same derived status and therefore the same
unproven condition — which is precisely what makes a deterministic authority
refusal reusable under §6.3 once, and only once, its basis is re-proved.

**Frozen stale wording is preserved, never repaired.** The project already
contains accepted artifacts whose internal status wording is historically frozen
at `CANDIDATE` while a separate closure or acceptance record establishes the
current status. The control plane records **both** — the frozen internal wording
and the governing evidence chain — and reports the divergence as recorded
document drift. It never edits the artifact, never rewrites the wording, and
never treats the drift as a downgrade.

**Unproven status is a first-class outcome.** Where the evidence chain is
missing, an artifact's status is recorded as *unproven* with the exact missing
evidence named. Unproven is never rendered as accepted, adopted, rejected, or
superseded.

| **AIC-1** | **Governing-set enumeration — first half of the one basis-establishment transaction** | Performed **once per establishment episode, by the single executing run that holds the `input_establishment_claim`** for the shared `verification_input_establishment_identity` — never once per attached caller — capture the enumerated set as that run's **tentative** input basis — **including every record that will be cited as status evidence**, so the recorded input set covers everything the outcome will depend on and a later re-proof can cover it too — together with the **tentative recorded authority-order identity and version** and the **tentative derivation-ruleset version** in force. Enumeration is recorded so a later reader can see exactly what was and was not checked. **No generation identity exists at this point, and none is preassigned or reserved.** | An enumeration that cannot be completed because a required governing record is **determinately absent** → the determinate absence is itself a recorded basis input, carried into the revalidation-and-seal step at AIC-2; the deterministic Outcome-B refusal naming that member commits at AIC-4 for the generation the sealed basis establishes, with the completed part preserved. An enumeration step that **could not be performed** → technical failure state: the durable technical failure record is appended **against `verification_input_establishment_identity`**, **no basis is sealed, no generation identity is established, no outcome commits, and nothing of the declaration family is locked** (§6.2 (b)); the incomplete enumeration is preserved as the record of what was checked, and any re-attempt runs only through that identity's own accepted-B9 group (§11) |
| **AIC-2** | **Identity verification, full revalidation, and basis seal — second half of the same transaction** | Append each member's recomputed-versus-recorded identity result. Append-once per {run, member}. Then perform the **mandatory full revalidation**: re-establish from the actual sources the authority-order identity and version, the ruleset version, the completed membership, every member identity, every status-evidence identity, every recomputed content identity, and every determinate absence, and compare the whole of it against the tentative basis. **Where the revalidation matches**, atomically **compare-and-commit that completed basis as sealed** under the `input_establishment_claim` — at most one sealed basis may ever commit for that input-establishment identity, and a duplicate basis commit **absorbs** against the already committed identical basis — and **only then derive `verification_generation_identity` from that sealed basis**, link it to the predecessor generation AIC-0 located, bind this run to it, and **converge every caller attached to that episode onto that same generation identity and its one-outcome fence — each still separately referenced by its own attachment record, and none of them re-performing any part of AIC-1/AIC-2** (§5, §9 AIC-4). | **Where the full revalidation cannot complete, or differs in authority order, ruleset version, membership, member identity, content identity, evidence identity, or determinate absence** → **no basis is sealed and no generation is established.** Both observations are preserved, and a technical and potentially retryable `input_basis_changed_during_establishment` — or the exact failed-revalidation condition — is appended against `verification_input_establishment_identity`; another attempt is permitted **only** through that operation's accepted-B9 group (§11). A **mismatch** between a recomputed and a recorded content identity, or a **determinately absent** member, is not that case: it is a determinate finding carried inside the sealed basis, and its deterministic Outcome-B refusal commits at AIC-4 for the generation that basis establishes. A member that **cannot be read at that moment**, or whose identity could not be recomputed because the attempt failed → technical failure state (§6.2 (b)): technical failure record appended against the input-establishment identity, **no refusal committed, no basis sealed, no generation identity established, and nothing may commit at AIC-4** |
| **AIC-3** | **Status derivation and contradiction detection** | Append each member's derived status with its evidence reference, and every contradiction/missing-evidence/unresolved finding, with conflicting evidence preserved by reference — all of it derived **from the sealed basis alone**. No input is re-read, refreshed, or substituted inside the established generation; a later change to a file belongs to a later request's re-proof and its successor generation and can neither alter nor misbind this generation's outcome. | Any determinate finding → deterministic Outcome-B refusal; nothing is resolved, ranked, or repaired. A step that could not be performed → technical failure state, no outcome committed |
| **AIC-4** | **Outcome commit (one compare-and-commit per generation)** | Atomically commit **exactly one** outcome for the `verification_generation_identity`, **on that generation's sealed basis and on nothing else**: the immutable snapshot record (Outcome A) or the immutable deterministic refusal record (Outcome B) — **at most one outcome ever for that generation, across every execution attempt of it**, which is the guarantee accepted B9 R2/§6 relies on when unlimited admitted attempts execute under one seam identity. **No outcome may commit before the basis-establishment transaction has sealed a fully revalidated basis and the generation identity has been derived from it** (AIC-1, AIC-2). The commit constraint is **never** placed on the content-blind `verification_question_identity`: a declaration family may therefore hold **several generations in chronological order, each with its own single outcome**, and that is neither a duplicate nor a contradiction. Concurrent runs of the **same** generation with identical verified inputs: exactly one winner commits; losers observe that generation's committed outcome and append nothing. Each committed outcome is recorded with the accepted B9 §3 class it supplies — a snapshot as **`terminal_success`**, a deterministic refusal as **`terminal_substantive`** (routing terminology only) — so B9 classifies this seam's durable outcome without guessing (§11.1). A technical failure state never reaches this boundary and commits nothing here. | No committed outcome → **no snapshot reference exists**, and no caller may proceed under this control plane's name |
| **AIC-5** | **Parent terminal and release** | Append the run's **single parent terminal operational log** — naming the durable outcome the run reached and the accepted B9 §3 class it supplies (§11.1) — then release the snapshot or refusal reference to the caller. Exactly one terminal per verification run (per execution), including a run that ended in a technical failure state or an unresolved `indeterminate_recovery_required` state — whose terminal records that stop and releases no reference. | Terminal absent → no release, no acknowledgement; recovery appends only the missing terminal (§12 row 4) |

**The commit fence:** a caller may cite an authority snapshot only after AIC-4
has committed and AIC-5 has released it. There is no path by which a partially
verified run yields a usable reference.

**The basis fence:** a `verification_generation_identity` exists only after the
AIC-1/AIC-2 transaction has fully revalidated its tentative basis from the actual
sources and atomically sealed it. Before that seal there is a committed
`verification_input_establishment_identity` and its claim, and nothing else; after
it, the generation's inputs are fixed and are never re-read, refreshed, or
substituted inside that generation.

**The shared-establishment fence:** before any basis is sealed, the unit of
duplicate prevention is the **establishment episode, not the caller**. Requests
that resolve to the same declaration family, the same
`establishment_episode_anchor`, the same authority-order and derivation-ruleset
source references, and the same operation class and version resolve to **one**
`verification_input_establishment_identity`, **one** live
`input_establishment_claim`, **one** execution of AIC-1/AIC-2, **one** sealed
basis, and **one** accepted-B9 retry group. A caller's own identity never enters
that derivation and therefore never splits the work; it is preserved instead as a
separate attachment reference on that one operation, and the claim's loser
re-reads committed state and attaches rather than starting a second operation
(§5, §10, §12 rows 23–24).

**The reuse fence:** a committed snapshot or a committed deterministic refusal
may be released to a later operation only after a completed AIC-0 re-proof
(§6.1, §6.3). An earlier record on its own is never sufficient authority — and
never a sufficient refusal — for a later operation. A re-proof that shows changed
canonical inputs is **not** a reuse and **not** a blocked duplicate, and it is
**not** itself a generation: it refuses reuse and starts a fresh
input-establishment operation whose sealed basis, if and when it seals, defines a
**successor generation** entitled to its own single outcome.

**The technical fence:** a technical failure state commits no outcome, closes no
generation, absorbs no later request, and is never released, cited, or reused as
a decision of any kind. Its only forward paths are a new run of the **same
generation** — where that generation's basis was sealed, and only on confirmed
unchanged canonical inputs, executing **AIC-3 through AIC-5 on that generation's
committed sealed basis and never AIC-1 or AIC-2** — or, where no basis was
sealed, a re-attempt of the **AIC-1/AIC-2 input-establishment seam under the same
shared `verification_input_establishment_identity`**, reacquiring that identity's
claim and serving every caller attached to that one episode.
Both run only through accepted B9's admission mechanics for the operation that
actually failed (§11).

**Duplicate prevention is by identity convergence, never by suppression.** Two
callers asking the same question at the same time, resolving to the **same open
generation**, receive the same outcome; neither causes a second verification of
record. **Before any generation exists, the same holds one level earlier**: two
callers asking the same question against the same fresh-establishment condition
resolve to the **same shared, caller-blind
`verification_input_establishment_identity`**, and therefore to one live claim,
one execution of the AIC-1/AIC-2 enumeration, identity checking, revalidation and
basis establishment, one sealed basis, and one accepted-B9 retry group — while
each caller stays separately referenced by its own attachment record and receives
its own release. **A caller's identity never splits shared work, and never
creates a second pre-generation source operation or a second retry group for work
another caller is already performing.** Across runs, that convergence is **demonstrated by recomputation at reuse
time** (§6.1, §6.3) rather than assumed from the earlier record — duplicate
prevention never becomes a way to carry an old governing set into a changed
world, never a way to let a transient failure harden into a decision, and — since
the one-outcome constraint sits on the content-bound generation and never on the
content-blind family key — **never a way to prevent a changed world from being
verified and committing its own outcome.**

## §11 — Timeout and retry

- **Technical failures of a verification step are a state, not an outcome.** An
  unreadable source at that moment, an identity that could not be recomputed
  because the attempt failed, a step interrupted, an unavailable snapshot
  service, or a step timeout is a **technical failure state** (§6.2 (b)): the run
  appends its durable technical failure record marked technical and potentially
  retryable, **commits no snapshot and no refusal**, and — where the generation
  input basis was already sealed — leaves that **generation** open and
  incomplete under its `verification_generation_identity`. Where the failure is
  what prevented the basis from being sealed, **no generation exists to leave
  open**, and the failure is recorded against the
  `verification_input_establishment_identity`: that pre-generation source
  operation is the one that stays open and incomplete with its recorded retryable
  failure, and its **own** accepted-B9 retry group serves it (§5, §6.2 (b)).
  Nothing of the declaration family is locked either way. This is the settled
  shape accepted B9 §1 and §7 already
  describe — a handled retryable technical failure is held for the retry policy,
  the source operation stays open with its recorded retryable failure, and B9's
  technical retry serves it only while that original operation remains open and
  incomplete.
- **Re-execution runs through accepted B9 and only through it.** The durable
  technical failure record is the outcome B9 classifies (`technical_retryable`,
  accepted B9 §3). For an **established generation**, B9's retry group binds to
  this component's own canonical source identity —
  `verification_generation_identity`, never the content-blind
  `verification_question_identity` (accepted B9 §4: one group per
  source-operation duplicate-prevention identity). The seam bound to that
  identity is the **post-seal outcome-completion seam AIC-3 through AIC-5**. An
  admitted attempt executes **those boundaries under that same generation
  identity** as a new `verification_run_identity` (accepted B9 R2: the seam's own
  boundaries under the seam's own canonical identity): it **enters at AIC-3** and
  derives status, detects contradictions, attempts the AIC-4 commit, and performs
  AIC-5 **using only that generation's already committed, immutable sealed
  basis**. It runs **no** AIC-0, AIC-1, or AIC-2, and therefore performs no
  enumeration, no live-source identity verification, no basis revalidation, no
  seal or reseal, no basis replacement, and no re-derivation of the generation
  identity; **AIC-1/AIC-2 remain exclusively the pre-generation
  input-establishment seam.** This design's AIC-4 is the duplicate-execution
  defence that lets unlimited attempts of that generation commit at most one
  outcome. **A B9-admitted re-attempt may execute under the same generation only
  where this source seam confirms that the complete canonical generation inputs
  are unchanged** (accepted values package §5, §10). That confirmation is a
  **read-only routing and admission prerequisite only**: it compares the current
  canonical-input observation against the complete sealed generation basis, it
  never becomes part of the old generation's execution, it never refreshes or
  replaces that basis, and it never authorises AIC-1 or AIC-2 under the old
  generation identity. Where it proves the inputs unchanged, the admitted run
  executes AIC-3 through AIC-5 **solely on the sealed basis**; a live-source
  change occurring after that confirmation cannot affect or misbind the old run,
  because that run performs no live-input reread at all, and such a change is
  handled only by a later completed confirmation or reuse re-proof and its
  successor-generation route. Where that confirmation completes and finds **any**
  changed canonical generation input, execution under the old generation and the
  old retry group is refused: the old generation is recorded as predecessor together with the changed observation as one
compare-and-commit `establishment_episode_anchor` record, and **exactly one
fresh shared `verification_input_establishment_identity` episode** anchored on it
runs instead — that one fresh episode alone executes AIC-1/AIC-2 against the
actual sources, and a concurrent equivalent confirmation observing the same
change adopts the same anchor and joins it rather than opening a second. **No
  successor generation is preassigned or reserved**; the **successor linked
  generation identity with its own new retry group** exists only once that
  operation fully revalidates and atomically seals its basis (§9 AIC-2), with
  normal initial-episode semantics in that new group, and attempts inside the old
  group are never continued, transferred, or renumbered.
  Where the unchanged-input confirmation **cannot** be completed, this seam fails
  closed: **no admission and no execution under the old group, and no default**
  (§14). Where **no basis was ever
  sealed**, the retry group is this component's **pre-generation** group, derived
  from {the shared, caller-blind `verification_input_establishment_identity`, the
  input-establishment operation class} (accepted B9 §4) — **one group per
  establishment episode, never one per caller, serving every caller attached to
  it**. Its original execution is the initial
  episode's **ordinal 1 by reference**; every re-attempt requires **B9's R1
  admission**, the **exact accepted `retry_budget_ref`**, the **recorded schedule
  class with no default**, and **proof that no live attempt exists for the
  group**; R2 then **reacquires the `input_establishment_claim`** and re-executes
  **only the AIC-1/AIC-2 input-establishment seam** under that same canonical
  identity, sealing a basis or failing again without committing any generation,
  snapshot, or refusal. That path never crosses AIC-4 and forecloses no outcome
  for the declaration family (§5, §6.2 (b)). B9 records the attempt's outcome at R3 from this component's
  durable evidence only. **This design admits, schedules, triggers, or counts no
  retry of its own; it creates no second retry system, no alternate execution
  path, and no retry values of its own.** Admission is B9's R1 alone, fail-closed
  exactly as B9 defines it — including B9's own refusal of any hidden automatic
  retry without a committed admission.
- **A deterministic authority refusal is not a technical failure and is never
  admitted as one.** A mismatch, a determinate absence, a contradiction,
  determinately missing evidence, or an unproven status is a committed Outcome-B
  refusal (§6.2 (a)). Repeating the run against the same evidence derives the
  same refusal. Only a genuinely changed, recorded evidence state produces a
  different outcome, and it does so as a **successor generation** — established
  only when a fresh input-establishment operation seals its fully revalidated
  basis — **with its own run of record and its own committed outcome**, never as
  an amendment and never as a retry of the refusal into a pass. A committed
  deterministic authority refusal is this seam's durable
  **`terminal_substantive`** outcome under accepted B9 §3 — **routing terminology
  only, and never a meaning judgment** — and it carries no adopted
  substantive-retry policy reference and no per-case substantive-retry
  authorization, so accepted B9's R1 fails closed on that route and no same-group
  machine re-execution of a refusal exists (§11.1).
- **Exhaustion and early stop leave the generation unresolved, never refused.**
  Where B9's bounded episode ends without a completed verification — the attempt
  allowance used, the elapsed deadline reached, or a recorded early stop — the
  generation stays open, unfinished, and unproven: no outcome commits, no
  snapshot exists, and truthful exhaustion is recorded by B9 under its own
  records. That is exactly what the accepted retry values require (stop, say why,
  keep the work record, preserve the unfinished state; *no fake success, no
  hidden failure, no endless retry*). Where the exhausted or early-stopped
  episode belongs to the **pre-generation** group, there is no generation to
  leave open at all: no basis is sealed, no outcome exists, the request stays
  unresolved, and truthful exhaustion is recorded under B9's own records exactly
  the same way. **Such an episode yields no fresh `establishment_episode_anchor`
  of its own** (§5): it is not authority, it is not a refusal, and it is not a
  licence for a caller to mint a second episode around B9's admission —
  continuation under that same identity is accepted B9's real-change path alone,
  while a genuinely changed world commits its own reuse-refusal /
  changed-observation anchor record and opens **one** new shared episode with its
  own new group under normal initial-episode semantics. Any continuation
  afterwards is B9's own real-change path under its accepted rules, with its
  canonical-input confirmation belonging to this seam. **This seam owns two source operations and therefore two canonical-input
  sets:**
  - for an **established generation**, the canonical inputs are the **complete
    sealed generation basis** — the declaration (declared operation class and
    declared artifact scope), the recorded authority-order identity and version
    in force, the derivation-ruleset version in force, the completed enumerated
    membership, and every enumerated member's revalidated content identity or
    recorded determinate absence, including every cited status-evidence record;
  - for the **shared pre-generation input-establishment episode**, the canonical
    inputs are narrower and are exactly those §5 names: the **family key** — the
    declaration {declared operation class, declared artifact scope} — the
    **`establishment_episode_anchor`** resolved for that episode, the exact
    authority-order and derivation-ruleset **source references to consult**, and
    that operation's class and version. **No caller's own identity is among
    them**, which is precisely what makes identical concurrent work one operation
    with one retry group. What is read **from** those references is that
    operation's output, never its canonical input.

  Each attempt's remeasurement from disk is therefore **not** a re-measurement
  inside one lifetime identity: it is the **read-only confirmation performed
  before admission**, which **confirms whether the open source operation's
  canonical inputs remain unchanged**. For an established generation it sits
  entirely outside the admitted run — the run itself reads no live source and
  executes only AIC-3 through AIC-5 on the sealed basis — and it neither
  refreshes nor replaces that basis. Confirmed unchanged inputs continue under
  the same source-operation identity and the same retry group; **input-altering
  changes create a new source-operation identity and a new retry group**, with
  normal initial-episode semantics, exactly as the accepted retry-values wiring
  requires — never a continuation or a renumbering of the old group. For a
  generation, such a change is a **successor generation linked inside the same
  unchanged declaration family** — including a change to the recorded authority
  order or to the ruleset version, which varies the generation and never the
  family key. A changed declaration is a different family key, and therefore a
  different generation and a different group, never a continuation of the old
  one.
- **The retry values are already accepted and are consumed, not reopened.** The
  accepted B9 retry-values wiring package
  (`NH_B9_RETRY_VALUES_WIRING_INTO_B9_B10_BHOLD_B24_v1_4_CANDIDATE.md`, recorded
  `PACKAGE_COMPLETE` for the retry-values wiring job by its closure receipt, and
  carried in the accepted Bundle 1 normalization record §9 and its closure
  record) supplies, at design level, the declared versioned retry-budget
  configuration that accepted B9's `retry_budget_ref` and `retry_policy_ref`
  slots reference: the per-episode attempt limit of 3 total technical attempts
  with per-episode ordinals 1–3 alongside permanent group-wide attempt numbering;
  the minimum waiting gaps of 10 seconds then 30 seconds (live chat) and 1 minute
  then 3 minutes (background/nightly); the elapsed deadlines of 7 minutes (live
  chat) and 15 minutes (background/nightly) as real stop deadlines racing the
  attempt limit, each episode's clock beginning at its own durable
  first-failure record; and exactly one careful substantive retry after a durable
  rejection record. **This design selects none of these values, changes none of
  them, and adds none.** B9's admission reference is therefore not unconfigured:
  it resolves to that accepted declared content, and B9's fail-closed rule for a
  missing or unreadable configuration reference is consumed unchanged.
- **The schedule class is consumed, never guessed.** Whether a verification run —
  or a pre-generation input-establishment attempt — is `live_chat` or
  `background_nightly` comes from the calling operation's own recorded execution
  context, exactly as the accepted values package requires; for a **shared**
  establishment episode that is the recorded execution context of the operation
  that holds the claim, carried as recorded and never averaged, merged, or
  re-derived from an attached caller's context; a missing or
  unreadable class means **no admission and no default class**, for either of
  this seam's two retry groups.
- **Still open, and left open here:** the **execution timeout of a source
  operation** — including a step of this control plane's own verification run —
  remains with its existing owner and its later configuration phase, exactly as
  the accepted values package §18 and its closure record §6 record it. Nothing
  here sets, implies, or biases such a timeout. Master/map/Defaults/`cursorrules`
  integration of the accepted values, and all implementation, likewise remain
  open and separately authorized (§19 item 7).
- **A timeout never yields a partial snapshot and never yields a refusal.** A run
  that times out has committed no outcome; the generation it was executing stays
  open under §6.2 (b) — or, where no basis had been sealed, no generation exists,
  nothing of the declaration family is locked, and the timeout is recorded
  against `verification_input_establishment_identity` and served by that
  identity's own accepted-B9 group — and the next run starts from AIC-0, with the
  reuse fences applying to any earlier committed snapshot or refusal exactly as
  in §6.1 and §6.3.


### §11.1 — Outcome classification supplied to accepted B9 (settled here)

Accepted B9 §3 classifies **each source operation's own durable terminal
outcome**, and states plainly that classification is *"mechanical routing, never
a judgment about meaning."* A source seam therefore owes B9 exactly one thing:
durable outcomes unambiguous enough to route. **This design supplies that
mapping. It is settled here and is no longer deferred back to the
already-complete B9 dependency**, so no classifier has to guess and no decision
this seam actually owns is pushed onto an accepted package.

| This component's own durable outcome | Accepted B9 §3 class | What follows under B9's accepted rules |
|---|---|---|
| **Committed authority snapshot** — Outcome A at AIC-4, for one `verification_generation_identity` (§9) | **`terminal_success`** | Never retried; a retry request for that same source identity **absorbs** against the committed result, which is exactly AIC-4's one-outcome fence. **Absorption inside the source identity is not the §6.1 cross-run reuse path:** a **later caller request** is a new question about the current world and still passes the current-input re-proof in full before that snapshot may be released to it (§6.1, §9 reuse fence). |
| **Durable technical failure record marked technical and potentially retryable** — §6.2 (b), at any step, including a failed or mismatched basis revalidation | **`technical_retryable`** | Retryable **only** through B9's R1 admission under the exact accepted `retry_budget_ref` and the recorded schedule class with no default: under `verification_generation_identity` where a basis had sealed, where the admitted attempt enters at **AIC-3** and runs AIC-3 through AIC-5 on the immutable sealed basis; otherwise under the shared, caller-blind `verification_input_establishment_identity`, where it re-executes **only** the AIC-1/AIC-2 seam (§5, §11). |
| **Committed deterministic authority refusal** — Outcome B at AIC-4, §6.2 (a), basis-complete or not | **`terminal_substantive`** | **Not machine-retryable.** This is B9 **routing terminology only** — see below. This seam supplies **no** adopted substantive-retry policy reference and **no** per-case substantive-retry authorization for such a refusal, so accepted B9's R1 **fails closed** on that route exactly as B9 requires, and **no same-group machine re-execution of a deterministic refusal exists**. |
| **Durable `indeterminate_recovery_required` terminal evidence** — a run whose own recorded evidence cannot establish whether a condition is determinate or technical, §6.2 (c) | **`indeterminate`** | **Never retried. Recovery-first and fail-closed**: no admission until this seam's own recovery resolves the state. No outcome is committed, nothing is reusable, and nothing may be released. |
| **A live dependency hold on this seam's own work** | **`dependency_blocked_held`** | Not retried; it waits on that block's **own** release interface. This design creates no hold, no release interface, and no queue around one, and it never re-expresses a hold as a technical failure or as an authority refusal. |
| **A §7Q / SACL refusal over this component's own records** (§15) | **`privacy_refused`** | Not machine-retryable and **never retried around**. Only a genuinely changed, recorded authorization state permits a new attempt, and that record belongs to the owning gate — never to this design, which holds no privacy authority and re-expresses, re-classifies, and retries nothing on that gate's behalf. |

**`terminal_substantive` is routing terminology, not a meaning judgment.**
Recording a committed deterministic authority refusal in that class says exactly
one thing: it is **not** a technical failure, and is therefore **not**
machine-retryable under a technical retry budget. It does **not** convert an
authority refusal into a meaning-level assessment, a B24-style substantive
judgment, or any claim about whether an artifact is correct, wise, complete,
safe, or substantively right — this design makes no such claim anywhere and
cannot (§8, §17.5, §18). The refusal remains what §6.2 (a) defines: a determinate
statement about the evidence **as read**, with the conflicting or missing
evidence preserved intact.

**A changed world is still handled where it has always been handled here.**
Because no substantive-retry authorization exists on this route, there is no
mechanism by which an old refusal is re-executed into a pass, and none is created
here. A genuinely changed current evidence state travels v1_7's unchanged
successor route instead: the §6.1 / §6.3 current-input re-proof refuses reuse,
commits its one-compare-and-commit reuse-refusal / changed-observation record as
the `establishment_episode_anchor`, and opens **one** fresh shared
input-establishment episode whose fully revalidated seal creates the **successor
generation** entitled to its own single outcome (§5, §6.1, §6.3, §9 AIC-2, §11).
**A refusal is never retried into a pass, never amended, and never re-dated.**

**`indeterminate_recovery_required` is durable evidence about the run, never a
third outward outcome.** The token is accepted B9 §3's own vocabulary for the
source-side state it classifies as `indeterminate`, consumed here rather than
invented. Recording it changes nothing the caller sees: the caller still receives
**Outcome B** exactly as the decision package §5 settles it — a stop naming the
exact condition — and the decision package's two-outcome rule is untouched
(§6, §6.2 (c), §13).

**Supplying the class is not admitting the retry.** What this section settles is
only the mapping from this seam's own durable outcomes to accepted B9's classes.
**Accepted B9's R0–R4 boundaries, its admission, its attempt counting, its retry
budgets and their resolution, its scheduling, and its disposition remain B9's
entirely**, consumed by reference, neither duplicated, extended, nor redesigned
here (§11, §17.13, §18). **B9's classification authority is likewise unchanged**:
B9 still classifies each source operation's durable outcome under its own §3
rules. What this section removes is the *ambiguity* — the mapping is stated by
the seam that owns the outcomes, so B9's classification is determinate rather
than a guess, which is exactly what accepted B9 §3 asks a source seam to make
possible. This design still admits, schedules, triggers, and
counts no retry of its own, creates no second retry system, and creates no
alternate execution path; a bypass of B9's admission remains B9's recorded
violation, not an alternative route.

## §12 — Crash recovery (lookup-first; idempotent; no rewrite; no false success; fail-closed on unreadable or contradictory evidence)

| # | Crash / condition | Resolution |
|---|---|---|
| 1 | Crash before any run record | Nothing to undo; no artifact was touched (the control plane never writes to governed artifacts); the next request runs AIC-0 normally |
| 2 | Enumeration committed, no verification results | Resume verification from the committed enumeration, or abandon the run by appending a run-abandoned entry with cause; either is safe because nothing was released |
| 3 | Partial verification results, no committed outcome | **No snapshot exists, no refusal exists, and neither is constructed from partial results.** Re-verify the unresolved members, or abandon; the partial results stay preserved as the record of what was checked |
| 4 | Outcome committed, parent terminal log missing | Append the missing AIC-5 terminal idempotently from the committed outcome; only then release. This is **lookup-first recovery of the missing terminal alone, not a B9 re-execution**: nothing is re-derived, nothing is re-read, and no attempt is admitted |
| 5 | Terminal exists, caller never received the reference | The outcome is durable: return the recorded snapshot or refusal to **that same run's caller**; nothing re-verifies; no second outcome. A different, later operation is a new request and passes the §6.1 / §6.3 reuse fences |
| 6 | Duplicate request after a committed snapshot | Absorbed into the open generation if one is open **and the request resolves to that same generation identity**, or — before any basis is sealed — against the committed sealed basis of the same shared `verification_input_establishment_identity` through its claim, and otherwise **attached** to that one live episode rather than starting a second; failing all of that, the AIC-0 re-proof decides: identical recomputed snapshot identity → the committed snapshot is returned with the re-proof recorded, no second run of record; any difference → reuse is refused, the predecessor reference and the changed observation are **committed as the one compare-and-commit anchor record**, and **one** fresh shared input-establishment episode anchored on it runs, joined rather than duplicated by any concurrent equivalent re-proof. **The re-proof opens no generation:** a successor generation exists only once that operation's revalidated basis is sealed, and that generation's run then produces its own outcome |
| 7 | Request after a committed **deterministic** refusal | The AIC-0 re-proof runs on the refusal's own basis (§6.3): the refusal is basis-complete **and** the recomputed `refusal_basis_identity` is identical → the recorded refusal is returned unchanged and the unproven condition is not re-litigated by repetition; not basis-complete, or any basis input changed, or the same condition no longer derives → reuse is refused and a **fresh input-establishment operation** runs, whose sealed basis establishes the successor generation whose run of record is free to commit its own outcome under the current evidence (§11) |
| 8 | Source artifact changed between two runs | The change is caught at the AIC-0 re-proof, because the recomputed content identity differs: **the earlier snapshot or refusal is not reusable and is never returned to the later operation.** Those changed inputs are handed to a **fresh input-establishment operation**, never to a generation the re-proof itself opens; the **successor generation exists only once that operation's fully revalidated basis is atomically sealed**, is linked to the predecessor located at AIC-0, and its run commits **its own** outcome under the sealed content identities; the earlier generation's record stays valid as a statement about the earlier moment, is never rewritten, and **never blocks the successor generation from committing** |
| 9 | Recorded identity and recomputed identity disagree | Integrity finding: deterministic Outcome-B refusal, both values preserved, nothing updated, nothing chosen |
| 10 | A governing member is determinately absent from the snapshot's source | Deterministic Outcome-B refusal naming the absent member; absence is never treated as "no constraint" |
| 11 | Two contradictory status records for one artifact identity | Unresolved authority state: deterministic Outcome-B refusal, both records preserved by reference, no winner selected (decision package §7) |
| 12 | An acceptance/closure record references an identity no artifact matches | Deterministic Outcome-B refusal: the mismatch is surfaced; no record is invented and no artifact is re-identified to fit |
| 13 | A snapshot is cited by a later operation but its own record is unreadable | Fail closed: the citation cannot be honoured; the citing operation has no proven authority; nothing is reconstructed from memory or summary |
| 14 | Concurrent runs race at AIC-4 | Exactly one commits; the loser observes and appends nothing; contradictory evidence *about the run itself* → unresolved, surfaced |
| 15 | Crash during recovery | Recovery-run identity + lookup-first over append-only records: repeats re-read committed state and re-apply nothing |
| 16 | An attempt to proceed without a committed, released snapshot | Refused and logged as a fail-closed event; no execution path exists under this control plane's name without AIC-4 + AIC-5 |
| 17 | Crash or failure **during** a reuse re-proof (snapshot or refusal), or a basis member unreadable/absent at re-proof time | The re-proof is incomplete, so nothing is proven: **the stored snapshot or refusal is not returned**, and the re-proof establishes no generation. The stop is classified under §6.2 — determinate absence → reuse refused, and a fresh input-establishment operation whose sealed basis carries that absence into a deterministic refusal; a failed read → a technical failure state committing nothing, recorded against the shared `verification_input_establishment_identity` — and the incomplete re-proof is preserved as the record of what was checked. No partial re-proof ever counts as proof |
| 18 | **Technical failure at any step, including a failed or mismatched basis revalidation; crash or interruption of a run** | No outcome is committed and none is inferred. Where the generation input basis had been **sealed**, the durable technical failure record (or, after a crash, the recovered evidence of an unfinished run) leaves that **generation open and unresolved** under its `verification_generation_identity`. Where the failure — including `input_basis_changed_during_establishment` or any failed revalidation — prevented that basis from being sealed, **no generation and no outcome exists and nothing of the declaration family is locked**; the failure is recorded against the **shared** `verification_input_establishment_identity`, and the crash or stop **releases or recoverably supersedes** that identity's live `input_establishment_claim` **without inventing a basis**. Recovery is lookup-first over the append-only records of what that attempt actually completed: a committed sealed basis is found and absorbed, never rebuilt, and because every input of that identity is committed state a re-derivation lands on the **same** identity rather than creating a second shared operation (row 24). One episode, one record set, one retry group, however many callers are attached. Re-attempt of a **sealed generation** happens only through accepted B9's R1 admission and only after this seam confirms the canonical inputs are unchanged, and it executes **AIC-3 through AIC-5 under the same generation identity on that generation's already committed immutable sealed basis** — no enumeration, no live-source identity verification, no basis revalidation, no reseal, no basis replacement, no re-derived generation identity, and never AIC-1 or AIC-2. A completed confirmation that finds changed canonical inputs refuses execution in the old group entirely and starts a fresh input-establishment operation whose seal alone yields the successor generation and its new group (§11). Re-attempt **before** a seal happens only through the pre-generation group's R1 admission — exact accepted `retry_budget_ref`, recorded schedule class with no default, no live attempt outstanding — re-executing **only the AIC-1/AIC-2 input-establishment seam** under the same input-establishment identity, which is the only path on which actual sources are re-read and revalidated (§6.2 (b), §11) |
| 19 | **A member unreadable at one attempt reads at the next (restored readability)** | Nothing special is required, and nothing is compared against the earlier failure, because that failure committed no refusal and locked no identity. Which path the new attempt takes depends on whether a basis had sealed. **Before any seal:** the admitted attempt re-reads and revalidates the actual sources **only** through the same pre-generation input-establishment operation's AIC-1/AIC-2 seam, and a generation exists only if that full revalidation matches and the basis seals — Outcome A or a deterministic refusal then follows at AIC-3/AIC-4 on that sealed basis. **After a seal:** the admitted attempt performs **no reread and no revalidation**; it continues at **AIC-3** on the immutable sealed basis and derives the outcome that basis proves, while a member that has since changed on disk belongs to a later completed confirmation or re-proof and its **fresh input-establishment operation and successor generation**, never to this run. The earlier technical failure record stays preserved as the honest record of that attempt and is never re-read as a decision |
| 20 | **A retry episode is exhausted or stopped early with the work still unresolved** | No outcome commits; no snapshot and no refusal exist. Where a generation had been sealed, it stays open, unfinished, and unproven; where the exhausted episode belongs to the **pre-generation** group, no basis is sealed and no generation exists at all, and the request simply stays unresolved. Truthful exhaustion is recorded under B9's own records in both cases. Callers have no proven authority and may not proceed. Continuation is B9's real-change path under its accepted rules, with this seam's two canonical-input sets as §11 states them — never a decided refusal manufactured from exhaustion, and never a bar on a changed world being verified as a successor generation |
| 21 | **A later request arrives while a generation is open only because of a technical failure** | It is absorbed into that open generation where it resolves to the **same generation identity** (§6.1, §9 AIC-0): it receives no snapshot, and it is **never** answered with a refusal, because none exists. Where the still-open work is a **pre-generation** input-establishment operation, the same request resolves to that same shared identity — the still-open-and-incomplete episode being its own `establishment_episode_anchor` under §5 case (c) — and is absorbed through that identity's committed sealed basis if one exists, and otherwise **attaches** to that one live episode under its own `establishment_caller_attachment` rather than starting a second live attempt or a second operation; the failed episode's AIC-1/AIC-2 work is never performed twice, and one accepted-B9 group continues to serve it. If it resolves to a different fresh-establishment condition or to different canonical inputs, or no work of that family is open, it begins a new run of record under whatever shared `verification_input_establishment_identity` its own condition resolves to, and under whatever successor generation that run's sealed basis defines |
| 22 | **The run cannot establish whether a condition is determinate or technical** | Recorded as **unresolved** (§6.2 (c)) and appended as the durable terminal evidence **`indeterminate_recovery_required`**, which is this seam's **`indeterminate`** outcome for accepted B9 §3 (§11.1): no outcome commits, nothing is reusable, nothing is released, and resolution is recovery-first. Under B9's accepted rules that class is **never retried — recovery-first and fail-closed, with no admission until this seam's own recovery resolves the state** — and this design admits no retry of its own in it. The record is evidence about the run, never a third outward outcome: the caller still receives Outcome B |
| 23 | **Two identical concurrent requests before any generation exists** | Both resolve the same `verification_question_identity`; both resolve the same `establishment_episode_anchor` from the same committed state; both therefore derive the **same shared, caller-blind `verification_input_establishment_identity`**. Exactly one wins the one-compare-and-commit `input_establishment_claim` and becomes the executing run; the other **re-reads the committed family and open-operation state and attaches** under its own `establishment_caller_attachment`, appending no second claim, no second operation, and no second AIC-1/AIC-2 execution. **The AIC-1/AIC-2 enumeration, live-source identity checking, revalidation, and basis establishment happen once**, and **one** accepted-B9 retry group serves any pre-seal technical failure of that episode. Both callers stay separately referenced; if the basis seals, both converge on the one derived `verification_generation_identity`, where at most one outcome commits. Where the anchor is a reuse-refusal record, that record is itself one compare-and-commit, so two concurrent re-proofs observing the same change reach one anchor and one episode; where the two requests resolve **different** fresh-establishment conditions they are not identical work, and each takes its own episode and its own group (§5, §9 AIC-0…AIC-4, §10, §17.8) |
| 24 | **Crash during anchor resolution, claim commit, or attachment** | Lookup-first over append-only committed state, and **no second shared establishment operation can arise for the same fresh-establishment condition**: every input of `verification_input_establishment_identity` is committed state — the family key, the committed anchor, the exact source references, the operation class and version — so a re-derivation after a crash lands on the **same** identity and finds whatever was committed. A claim committed with no further progress is found and either resumed under B9's admission or released/recoverably superseded **without inventing a basis** (row 18); a committed sealed basis is found and absorbed, never rebuilt; an attachment appended without a released reference is honoured from the committed outcome, never re-executed. A half-observed reuse-refusal anchor record is **re-read, never re-minted**: its one-compare-and-commit key {family key, predecessor generation identity, recomputed changed-input observation} makes a second identical record impossible, so a crash cannot split one fresh-establishment condition into two episodes, two claims, or two retry groups |

## §13 — Partial completion

- A partially completed verification **never** produces authority. It produces
  either a resumable run (§12 rows 2–3, 18) or an Outcome-B stop naming exactly
  which members were unverified and under which §6.2 class it stopped.
- A **technical failure state is never a partial outcome and never becomes one.**
  It commits nothing, closes nothing, and hardens into nothing — not by
  repetition, not by waiting, not by exhaustion (§6.2, §11, §12 rows 18–20).
  Where it prevented the generation input basis from being sealed, it commits
  **no generation outcome**: there is no generation identity to lock, the
  content-blind declaration-family key acquires no constraint, and the family
  stays free to verify the current world as a successor generation. It is not, however, unowned work: it belongs to the **shared**
  `verification_input_establishment_identity` resolved and committed at AIC-0 for
  that establishment episode, its executing run holds that identity's claim,
  every attached caller stays separately referenced, and it is re-attemptable
  only through that identity's **one** accepted-B9 retry group — never one group
  per caller (§5, §6.2 (b), §11).
- **An unsealed basis is never a partial generation.** A tentative basis, a
  partial enumeration, and a partial set of identity results derive no generation
  identity and commit no outcome; they are preserved as the honest record of what
  was checked, and only a fully revalidated, atomically sealed basis ever becomes
  a generation (§9 AIC-1, AIC-2). An **attachment** is likewise never partial
  work and never a second attempt: it records that a caller joined the one shared
  episode, and it performs and proves nothing on its own (§5, §10).
- A partially completed **reuse re-proof** likewise proves nothing: it never
  releases the earlier snapshot and never releases the earlier refusal, and the
  members it did check are preserved as the honest record of what was checked
  (§12 row 17).
- The record of a partial run is preserved: what was enumerated, what was
  verified, what was not, and why it stopped. This is the honest account of an
  incomplete check, not a weakened pass.
- No "provisional", "degraded", "assumed", or "inherited" authority state
  exists. The decision package §5 permits two outcomes only.
- A partial run never mutates any artifact, any prior snapshot, or any prior
  refusal.

## §14 — Fail-closed matrix

| Condition | Behaviour |
|---|---|
| A governing member is **determinately absent** or unidentifiable from readable evidence | Deterministic Outcome-B refusal; no snapshot; the member is named; the refusal's basis records the determinate absence |
| A governing member **cannot be read at that moment**, or its identity cannot be recomputed because the attempt failed | **Technical failure state** (§6.2 (b)): no snapshot, **no refusal committed**; where the basis had been sealed, that generation is left open and unresolved; where the failure prevented the basis from being sealed, **no generation identity is established and nothing of the declaration family is locked**, and the failure is recorded against `verification_input_establishment_identity`. Nothing is reusable; re-attempt of a sealed generation only through accepted B9's R1 admission on confirmed unchanged canonical inputs, executing **AIC-3 through AIC-5 on that generation's sealed basis and never AIC-1 or AIC-2**, and otherwise only through the pre-generation accepted-B9 group of that input-establishment identity (§5, §11) |
| Recorded and recomputed content identity disagree | Deterministic Outcome-B refusal; both preserved; nothing updated |
| Status evidence is determinately missing for a member | Status recorded as unproven; deterministic Outcome-B refusal; the missing evidence is named |
| Two records contradict about one artifact | Unresolved authority state; deterministic Outcome-B refusal; both preserved; no winner chosen |
| Only inadmissible proof exists (placement, wording, summary, absence of contrary record) | Treated as no proof; deterministic Outcome-B refusal |
| Enumeration cannot be completed because a required governing record is determinately absent | Deterministic Outcome-B refusal; the completed part of the enumeration preserved |
| Enumeration cannot be completed because a step could not be performed | Technical failure state recorded against `verification_input_establishment_identity`; **no basis is sealed and no generation identity is established**; no outcome committed; nothing of the declaration family locked; the incomplete enumeration preserved; re-attempt only through that identity's own accepted-B9 group |
| The **full revalidation** of a tentative input basis cannot be completed, or differs in authority order, ruleset version, membership, member identity, content identity, evidence identity, or determinate absence | **No basis is sealed and no generation is established.** Both observations are preserved; a technical and potentially retryable `input_basis_changed_during_establishment`, or the exact failed-revalidation condition, is appended against `verification_input_establishment_identity`; no outcome commits, nothing is reusable, and another attempt is permitted only through that operation's accepted-B9 group (§9 AIC-2, §11) |
| A **pre-generation** re-attempt lacks accepted B9's R1 admission, the exact accepted `retry_budget_ref`, or the recorded schedule class, or a live attempt already holds the `input_establishment_claim` | **No admission, no default class, and no second live attempt.** The input-establishment seam fails closed exactly as accepted B9 requires; nothing is sealed, no generation is established, and the fail-closed event names the missing reference or the outstanding live attempt (§5, §11) |
| The derivation ruleset version in force cannot be established | No snapshot may claim a ruleset it cannot name: an Outcome-B stop, classified under §6.2 — determinately unestablishable from readable evidence → deterministic refusal; a failed read → technical failure state |
| A later operation asks for an existing snapshot and the current-input re-proof cannot be completed | The stored snapshot is **not** returned; Outcome-B stop naming the condition under its §6.2 class; there is no fallback to the earlier record |
| A re-proof shows changed membership, a changed member identity, a changed recorded authority order, or a changed ruleset version | The stored snapshot or refusal is **not** returned, and **the re-proof establishes no generation**; those changed canonical inputs commit their reuse-refusal / changed-observation record as the one compare-and-commit `establishment_episode_anchor` and start **exactly one fresh shared `verification_input_establishment_identity` episode** anchored on it, and the successor generation — linked to its predecessor inside the same declaration family — exists only once that episode's fully revalidated basis is sealed, after which its run of record may commit **that generation's own** outcome; nothing is amended and no earlier record is re-dated |
| A B9-admitted re-attempt cannot confirm that an established generation's canonical inputs are unchanged, or that confirmation is incomplete | **No execution under that generation: no admission and no default.** Where the confirmation completes and proves the inputs unchanged, the admitted run executes **only AIC-3 through AIC-5 on that generation's committed sealed basis**. Where it completes and shows changed canonical inputs, the old generation and its retry group are not continued, transferred, or renumbered; the old generation is recorded as predecessor with the changed observation, a **fresh input-establishment operation** runs and alone executes AIC-1/AIC-2 against the actual sources, and the **successor generation identity with its own new retry group** comes into existence only when that operation's fully revalidated basis is sealed, with normal initial-episode semantics in the new group (§11) |
| A later operation asks for an existing refusal that is **not basis-complete**, or that arose from a technical failure or unresolved state | The refusal is **not** reused and never absorbs the request; a new run of record proceeds under the current evidence, under whatever shared input-establishment identity its own fresh-establishment condition resolves to and under whatever generation that episode's sealed basis defines (§6.3) |
| A refusal-basis re-proof cannot be completed, or does not reach the identical `refusal_basis_identity` | The stored refusal is **not** returned; where the re-proof completed and the basis changed, a **fresh input-establishment operation** proceeds and its sealed basis establishes the successor generation whose run may commit its own outcome; where the re-proof could not complete, the stop is recorded under its §6.2 class against the input-establishment identity; there is no fallback to the earlier refusal, and the re-proof opens no generation of its own |
| The run cannot establish whether a condition is determinate or technical | Recorded unresolved and appended as the durable `indeterminate_recovery_required` terminal evidence — this seam's **`indeterminate`** outcome for accepted B9 (§11.1); no outcome commits, nothing is reusable, nothing is released, recovery-first, and under B9's accepted rules never retried and no admission until recovery resolves the state |
| A retry episode is exhausted or stopped early with the work unresolved | No outcome; no snapshot; no refusal; truthful exhaustion recorded; the unfinished state preserved; no caller may proceed. Where a generation had been sealed it stays open and unresolved; where the exhausted episode is the pre-generation group's, no basis is sealed and no generation exists. A changed world is still verifiable as a successor generation |
| A caller proceeds without a committed and released snapshot | Refused and logged as a fail-closed event (§12 row 16) |
| A request would require the control plane to choose between contradictory governing evidence | Refused; choosing is prohibited (decision package §7) |
| An `establishment_episode_anchor` cannot be resolved from committed state — including a request arriving after a pre-generation episode was exhausted or stopped early with nothing sealed and no committed change record | **No fresh episode is minted, and no default anchor exists.** Nothing is sealed, no generation is established, no outcome commits, and nothing becomes reusable; the request is recorded **unresolved**, truthful exhaustion stays preserved under B9's own records, and continuation under that same identity is accepted B9's real-change path alone — never a fresh episode created here to walk around admission. A genuinely changed world still commits its own reuse-refusal anchor record and opens one new shared episode with its own new group (§5, §11, §12 rows 20 and 23) |
| A request would derive a **caller-specific** pre-generation identity, or open a second establishment operation for a fresh-establishment condition one shared operation already covers | Refused. `verification_input_establishment_identity` is **caller-blind by derivation**, its claim is one compare-and-commit, and the loser **attaches** rather than duplicating; a second live attempt, a second claim, a second AIC-1/AIC-2 execution, or a second accepted-B9 retry group for that same identity has no admissible path, and the attempt is logged as a fail-closed event. Caller identities are preserved as separate attachment references, never merged and never discarded (§5, §9 AIC-0, §10, §12 rows 23–24) |
| A request would require the control plane to write to, repair, or normalise any artifact | Refused; writing is prohibited (§18) |

Fail-closed always means: **preserve the conflicting evidence, surface the exact
problem, produce no authority** — and never let a failure to look become a
statement about what was seen.

## §15 — Authority and privacy gates

- **Over its own records.** Ledger entries, snapshots, refusals, technical
  failure records, and operational logs are living memory under Master §0B and
  are governed by §0B's ACCESS AND AUTHORIZATION BOUNDARY: permanent recording
  and connection do **not** by themselves grant runtime access. Access remains
  subject to §7Q protection rules (including the visible-output versus internal-use
  distinction), Level-1 protected-boundary restrictions, §25 identity and security
  authorization (BAI / SACL / SIA) where applicable, TSC blockers, and any
  separate influence-removal instruction.
- **Level-1 discipline.** Where any verified artifact or its location touches
  Level-1 material (live secrets, credentials), records reference it by opaque
  identifier only and never expose raw content, physical location, or access
  path (Master §0A / §0B / §7Q). A technical failure record names the condition
  and the step under the same discipline; it never becomes a channel for
  otherwise protected content.
- **Order preserved.** Where this control plane's own output is ever delivered
  as visible output, the settled output order is unchanged: §7Q first as the
  first sequential factor, SACL second. This design neither reorders those
  factors nor inserts itself among them.
- **It is not a gate.** The control plane holds no privacy authority, no access
  authority, no promotion authority, and no write-validation authority. It
  reports recorded permission state (§4.2 item 11); enforcement stays with the
  modules that already own it (`cursorrules` §1A). A privacy or access refusal
  encountered by any adjacent mechanism stays that gate's own recorded outcome
  under accepted B9 §3's `privacy_refused` class and is never re-expressed,
  re-classified, or retried around here. Where a §7Q / SACL refusal falls on
  **this component's own records**, that is likewise this seam's
  **`privacy_refused`** outcome for B9 (§11.1): not machine-retryable, never
  retried around, and re-attemptable only on a genuinely changed, recorded
  authorization state that belongs to the owning gate and never to this design.
  A live **dependency hold** on this seam's own work is likewise its own class,
  **`dependency_blocked_held`**, waiting on that block's own release interface —
  neither is ever re-expressed as a technical failure or as an authority
  refusal.

## §16 — Component-specific §0B logging

Under Master §0B: **one real operation, one log**; **no double evidence**; no
log-about-logging; logs are living memory subject to §7Q/§25 access rules;
active/cold state follows declared cooling rules that N.H may only *propose*
changing and Ness approves.

- **Canonical state records** (ledger entries, snapshot records, deterministic
  refusal records, durable technical failure records) are machine facts, **not**
  operational logs, and never additional evidential votes.
- **Every real operation of this control plane emits exactly one append-only
  operational log** under its own identity: child logs for enumeration, identity
  verification, **basis revalidation and sealing**, status derivation,
  contradiction detection, **current-input re-proof**, **technical failure
  recording**, and recovery resolution — each under its own child operation
  identity referencing the parent verification run, and the pre-generation ones additionally referencing the shared `verification_input_establishment_identity` they
  execute under — one shared identity per establishment episode, so the
  AIC-1/AIC-2 child logs are emitted **once for that episode and never once per
  attached caller**; **AIC-5 is the single parent terminal.**
- A verification log never makes any artifact more authoritative, more accepted,
  more certain, or more correct. Verifying an artifact ten times produces ten
  operational records and zero additional weight. A re-proof is likewise
  operational evidence of a check, never additional weight for what it checked,
  and a repeated technical failure is evidence of repeated failure only — never
  evidence about the artifact.
- **An established-generation retry emits only the records for the post-seal
  steps it actually executes** — the child-operation logs for status derivation,
  contradiction detection, and the outcome commit, plus its own single AIC-5
  parent terminal. Because it runs no AIC-0, AIC-1, or AIC-2, it emits **no**
  enumeration record, **no** identity-verification record, **no**
  basis-revalidation record, and **no** basis-seal record; those belong to the

- Logs of the caller's own operation belong to the caller under the caller's
  identities; logs and records of B9's admission, attempt, and disposition belong

  neither.

## §17 — Design-level wiring delta

Design language only; nothing here is code, and nothing here is integrated into
the Master or the Design and Wiring Map.

### §17.1 Connection

Three connection kinds exist, and no others:

1. **Caller ↔ control plane** — any operation that must prove which files govern
   it asks for a pre-operation check and receives a snapshot reference or a
   stop that names the exact unproven condition.
2. **Control plane → artifacts** — **read-only observation**. The control plane
   opens artifacts to recompute identity and to read their own recorded status
   evidence, both during a verification run and during a reuse re-proof. It has
   no write connection to any artifact, ever.
3. **Control plane → its own records** — append-only writes to its own ledger,
   snapshots, refusals, technical failure records, and §0B logs.

A fourth relationship exists but is not a connection this design builds: accepted
**B9** consumes this component's durable outcome and, where it admits an attempt,
re-executes this component's own boundaries under its own canonical identity
(§11). That is B9's accepted mechanism referenced, not a new path.

### §17.2 Direction

- Caller → control plane: request, carrying the caller's identity by reference.
- Control plane → artifacts: **one-way read**. No back-channel, no annotation,
  no marker written beside an artifact, no status stamped into a file.
- Control plane → caller: snapshot reference **or** a stop naming the exact
  unproven condition. Never a decision, never a permission, never an instruction.
- Control plane → §0B living record: append-only.
- Control plane → B9: its own durable records, **each recorded with the accepted
  B9 §3 class that outcome supplies** (§11.1), read by B9 as evidence under B9's
  rules. Stating that mapping is what a source seam owes B9 and is settled here;
  B9's classification authority, admission, attempt counting, budgets,
  scheduling, and disposition are unchanged, and this design takes **no**
  admission decision from B9 and makes none of its own.

### §17.3 Trigger

- **Pre-operation, caller-initiated only.** The check runs because an operation
  is about to act and must first prove its governing set. The reuse re-proof
  (§6.1, §6.3) is part of that same caller-initiated request, not a separate
  schedule.
- **A re-attempt after a technical failure is B9-admitted, never self-triggered
  here** — whether it executes a sealed generation's **AIC-3 through AIC-5** on
  that generation's committed sealed basis, or only the pre-generation
  AIC-1/AIC-2 input-establishment seam, which is the sole path that re-reads the
  actual sources. This design starts no
  attempt of its own, holds no timer, and counts no attempt; admission is
  accepted B9's R1 under its accepted values, and a bypass of that admission is
  B9's recorded violation, not an alternative path.
- **No autonomous scheduling, no background sweep, and no self-initiated
  re-verification is designed here.** Whether any scheduled or triggered
  re-verification ever exists is open (§19) and would need its own authority;
  Master §10-equivalent pull-sovereignty discipline (`cursorrules` §10: no new
  autonomous background task without explicit approval) applies to any such
  future path.
- A snapshot is **not** self-refreshing and has no invented expiry. Staleness is answered by proving the current inputs at reuse time and, where they differ, by
  one fresh shared input-establishment episode — anchored on the committed
  reuse-refusal record, so concurrent equivalent re-proofs open one and not two —
  whose sealed basis defines a **successor generation** whose own run produces its
  own outcome — never by mutating an
  existing one, never by a re-proof opening a generation of its own, and never by
  refusing the changed world an outcome of its own.

### §17.4 Operation identity

- One `verification_question_identity` per declared question — the content-blind
  **stable declaration-family lookup key**, derived from {declared operation
  class, declared artifact scope} and **nothing else**, which locates open
  generations and prior outcomes, carries **no** one-outcome constraint, and is
  **not** the identity B9's retry group binds to (§5).
- One `establishment_episode_anchor` per fresh AIC-1/AIC-2 establishment episode
  of a family — resolved at AIC-0 from committed state alone and never from a
  clock, a nonce, a duration, or any invented value, and spent by its own episode
  (§5).
- One `verification_input_establishment_identity` per **shared pre-generation
  establishment episode** — **not** one per caller request — this component's
  **caller-blind** canonical source-operation identity before a generation
  exists, derived from {family key, `establishment_episode_anchor`, exact
  authority-order source reference, exact derivation-ruleset source reference,
  input-establishment operation class and version}, resolved and committed at
  AIC-0, fenced by its one-compare-and-commit `input_establishment_claim`, and
  carrying **one** accepted-B9 retry group with the exact accepted budget
  reference, the recorded schedule class, and one live attempt at a time (§5,
  §11). Identical concurrent requests converge on it; the claim's loser re-reads
  committed state and **attaches** rather than opening a second operation.
- One `establishment_caller_attachment` per {shared establishment identity,
  caller} — caller identities are preserved as **separate references** on the one
  shared operation and are never merged, discarded, or turned into a second
  identity, a second claim, or a second retry group (§5, §10).
- One `verification_generation_identity` per **sealed** current-input generation
  of that family — the **content-bound source-operation identity** under which at
  most one outcome ever commits, and the source-seam identity B9's retry group
  binds to for an established generation (§5, §9 AIC-4, §11). Its inputs include
  the recorded authority-order identity and version and the derivation-ruleset
  version, so a change to either is a **successor generation inside the same
  family**, with its own new source-operation identity and its own new retry
  group; the same is true of any change of membership, member identity, content
  identity, determinate absence, or cited evidence record.
- One `verification_run_identity` per execution, bound to exactly one **shared**
  input-establishment identity resolved at AIC-0 — with exactly **one** such run
  per establishment episode holding the claim and executing AIC-1/AIC-2, while
  every other equivalent request attaches instead of executing — and to exactly
  one generation once that generation's basis is **sealed**, with child
  identities per executed step
  (§5), following the accepted parent/child pattern already in use; a reuse
  re-proof is a bounded child operation under `input_reproof_identity` and
  establishes no generation of its own; a B9-admitted re-attempt of an
  **established generation** is a new run bound **directly** to the **same
  generation identity**, admitted only on confirmed unchanged canonical inputs,
  entering at **AIC-3** and running AIC-3 through AIC-5 on that generation's
  committed sealed basis — binding no new input-establishment identity, acquiring
  no claim, and executing no AIC-0, AIC-1, or AIC-2 — while, before any seal, a
  re-attempt is a new attempt of the **same input-establishment identity**
  re-executing only the AIC-1/AIC-2 seam.
- The caller's identity is carried **by reference only**, is **never an input to
  any shared duplicate-prevention identity of this component**, and is never
  issued, adopted, replaced, merged, or discarded by the control plane; several
  callers attached to one shared establishment episode each remain separately
  referenced. B9's own group, attempt, and request identities likewise stay B9's,
  referenced only.
- The eventual common operation envelope belongs to Addition 2 (the Unified
  Durable Operation Kernel), which is **not designed** — see §17.13.

### §17.5 Data and meaning carried

- **Toward the control plane:** the caller's declared operation class, its
  declared artifact scope, and its identity reference. No memory content, no
  reading, no root, no telling, no personal material is required by or supplied
  to this mechanism.
- **Away from the control plane:** either (a) the verified governing set plus the
  snapshot reference, or (b) a stop naming the exact unproven condition.
- **Meaning carried:** *"these exact artifact identities were verified at this
  moment, and this is the evidence for each one's status."* Where an existing
  snapshot is released to a later operation, the meaning is *"these exact
  identities were verified at the earlier moment and were proven unchanged now."*
  Where a stop is a deterministic refusal, the meaning is *"this exact evidence,
  as read now, does not prove authority, for this named reason"* — and where such
  a refusal is reused, *"that exact evidence was proven unchanged now."* Where a
  stop is a technical failure state, the meaning is strictly *"this check could
  not be performed at this moment; nothing was decided"* — never a statement
  about any artifact. Nothing more. A snapshot carries **no** claim that any
  artifact is correct, wise, complete, safe, or substantively right; it carries no
  permission; and it never functions as evidence about the truth of anything the
  artifacts describe (Master §0B no-double-evidence).

### §17.6 Authority and privacy gates

As §15: the control plane's own records sit under §0B/§7Q/§25 access rules; it
holds no gate authority itself; the §7Q-first-then-SACL output order is
unchanged; Level-1 material is referenced by opaque identifier only.

### §17.7 Transaction boundary

AIC-0 … AIC-5 (§9), with **AIC-1 and AIC-2 as one deterministic
basis-establishment transaction** — capture a tentative basis, fully revalidate
it from the actual sources, then atomically compare-and-commit it as sealed under
the `input_establishment_claim` and derive the generation identity from that
sealed basis — with AIC-4 as the single compare-and-commit outcome fence **per
`verification_generation_identity`** — never per declaration-family key — and
AIC-5 as the single terminal-and-release per execution. No outcome may reach
AIC-4 before that transaction has sealed a fully revalidated basis and its
generation identity has been derived from it (AIC-1, AIC-2), and AIC-3 and AIC-4
read that sealed basis and nothing else. **AIC-1 and AIC-2 belong exclusively to
the pre-generation input-establishment seam and are never executed under an
existing generation identity; an admitted established-generation retry therefore
enters at AIC-3 and runs AIC-3 through AIC-5 on the committed sealed basis.** A reference exists only after both fences. **The shared-establishment fence
applies before all of them:** the pre-generation unit of duplicate prevention is
the establishment episode, not the caller, so requests resolving to the same
family key, the same `establishment_episode_anchor`, the same source references,
and the same operation class and version share **one** caller-blind
`verification_input_establishment_identity`, **one** live claim, **one**
execution of AIC-1/AIC-2, **one** sealed basis, and **one** accepted-B9 retry
group, with each caller preserved as a separate attachment reference (§5, §9,
§10). For a later operation, the AIC-0 reuse fences apply in addition: an
earlier committed snapshot reaches a new caller only through a completed re-proof
of its snapshot identity (§6.1), and an earlier committed deterministic refusal
only through a completed re-proof of its refusal basis (§6.3); a re-proof showing
changed inputs releases no earlier record and **opens no generation** — it starts
a fresh input-establishment operation instead. The technical fence applies
throughout: a technical failure state crosses no boundary, commits nothing, locks
no identity, and is never released.

### §17.8 Duplicate prevention

Identity convergence at every point (§10): one entry lineage per logical
artifact, one family key per declaration, one `establishment_episode_anchor` per
fresh establishment episode, **one shared, caller-blind input-establishment
identity per fresh establishment episode — never one per caller request — with
one live claim, one execution of AIC-1/AIC-2, at most one sealed basis committed
under it, and one accepted-B9 retry group**, one attachment per {shared identity,
caller}, one generation per sealed current-input basis, **at most one committed
outcome per generation** across every attempt of it, one snapshot per identical
verified input set, one terminal per execution, one log per operation. Absorption
inside one open generation prevents a second verification of record for that same
open generation, and before any seal the shared identity and its
`input_establishment_claim` do the same for the pre-generation operation: two
identical concurrent requests converge on **one** identity; one of them wins the
claim and performs the AIC-1/AIC-2 enumeration, identity checking, revalidation,
and basis establishment **once**; the other re-reads the committed state and
**attaches**; and a duplicate attempt arriving after the seal absorbs the
committed sealed basis rather than producing a second one. Each caller stays
separately referenced by its own attachment record throughout, and all of them
converge on the sealed generation and its one-outcome fence. **A caller identity
never creates a second pre-generation operation and never splits identical
concurrent work into two retry groups.** Across runs, an existing
snapshot or refusal is reused only where the re-proof demonstrates that the
canonical inputs are genuinely unchanged, and a changed input set is verified as
a **successor generation** with its own single outcome once its basis seals.
Duplicate prevention therefore never carries stale authority forward, never lets
a transient failure be reused as a decision, and never bars a changed world from
being verified at all.

### §17.9 Timeout and retry

Technical failures are recorded as a durable, retryable **state** that commits no
outcome and leaves the **established generation** open — or, where the failure
prevented the basis from being sealed, leaves no generation and no family-level
lock, the failure being recorded against `verification_input_establishment_identity`
(§6.2 (b)); re-execution routes to the accepted B9 mechanism under B9's admission
rules, **never to the content-blind family key**, through one of this seam's two
groups: for a sealed generation, B9's group is bound to
`verification_generation_identity` and each admitted attempt executes
**AIC-3 through AIC-5** under that same generation identity, entering at AIC-3
and consuming **only that generation's already committed immutable sealed
basis** — never AIC-1 or AIC-2, and therefore no enumeration, no live-source
identity verification, no basis revalidation, no reseal, no basis replacement,
and no re-derived generation identity — and only once this seam's read-only
confirmation shows the generation's canonical inputs unchanged (changed inputs
mean refusal in the old group, a fresh input-establishment operation that alone
re-reads the actual sources, a successor generation at its seal, and a new group
with normal initial-episode semantics; an incomplete confirmation fails closed
with no admission and no default); before any seal, B9's group is bound to the **shared, caller-blind**
`verification_input_establishment_identity` {that identity, the
input-establishment operation class} — **one group per establishment episode,
never one per caller** — with the original execution as the initial episode's
ordinal 1 by reference, R1 admission on the exact accepted
`retry_budget_ref` and the recorded schedule class with no default, at most one
live attempt, and R2 reacquiring the claim to re-execute **only** the AIC-1/AIC-2
seam. The **accepted B9
retry-values** (attempt limits, minimum waiting gaps, elapsed deadlines, and the
one careful substantive retry) are consumed by reference from the accepted values
package and its closure receipt; no value is chosen, changed, or added here, and
no retry is admitted, scheduled, or counted here. Source-operation execution timeouts stay
with their existing owners and remain open, as do the later integration and
implementation of the accepted values. A deterministic authority refusal is not a
technical failure, is never admitted as one, and is never retried into a pass
(§11). **The class each of this seam's own durable outcomes supplies is settled
at §11.1** — `terminal_success` for a committed snapshot, `technical_retryable`
for a durable technical failure record, `terminal_substantive` for a committed
deterministic refusal (routing terminology only, with no substantive-retry policy
or authorization reference and therefore no same-group machine re-execution),
`indeterminate` for a durable `indeterminate_recovery_required` state,
`dependency_blocked_held` for a live hold, and `privacy_refused` for a §7Q / SACL
refusal — and none of that is admission, counting, or scheduling, all of which
remain B9's.

### §17.10 Crash recovery

Lookup-first over append-only records; twenty-four rows at §12; no reconstruction
from summary; no partial-result snapshot; no partial re-proof counted as proof;
no technical failure hardened into a refusal; no content-blind lifetime lock
created by any failure; **no generation derived from an unsealed basis, and a
live `input_establishment_claim` released or recoverably superseded after a crash
without a basis ever being invented — a committed sealed basis being found and
absorbed, never rebuilt**; **no second shared establishment operation created by
a crash, because every input of that identity is committed state and a
re-derivation lands on the same identity, while a half-observed reuse-refusal
anchor record is re-read rather than re-minted** (§12 rows 18, 23, 24); no false
success.

### §17.11 Partial completion

Never yields authority; resumable or stopped; a technical failure state is never
a partial outcome; the partial record is preserved as an honest account (§13).

### §17.12 Fail-closed behaviour

Twenty-three conditions at §14. Fail-closed always preserves conflicting evidence,
surfaces the exact problem, produces no authority, and never converts an
inability to look into a statement about what was seen.

## §18 — Boundaries and must-nevers

The decision package §7 must-nevers, carried and binding. The Authority
Integrity Control Plane must never:

- decide that a candidate is accepted or adopted merely because its wording
  sounds final;
- edit a governing, accepted, or historical file;
- repair a contradiction silently;
- select a policy winner when the governing evidence is genuinely contradictory;
- invent a missing acceptance record;
- turn repository placement into authority by itself;
- treat a model's summary as proof of file state;
- overwrite history while reconciling status.

When evidence is incomplete or contradictory, it must **fail closed, preserve
the conflicting evidence, and surface the exact problem.**

Additional boundaries carried from the governing files and binding on this
design:

- **It creates no architectural authority.** It verifies and exposes the
  authority that Ness and the governing records already established (decision
  package §6).
- **It never lets an earlier verification stand in for a current one.** A stored
  snapshot is never released to a later operation without a completed
  current-input re-proof, a stored refusal is never released without a completed
  refusal-basis re-proof, and a remembered result is never treated as evidence
  about the present (Master standing lesson; Defaults §0).
- **It never records a failure to look as a statement about what was seen.** A
  technical read, recomputation, revalidation, service, interruption, or timeout
  failure is never committed as a refusal, never absorbed against, never allowed
  to harden into a decision by repetition, waiting, or exhaustion, and never
  allowed to create a content-blind lifetime lock over a declaration that has no
  established generation (§6.2, §11). It is equally never left ownerless: before a
  generation exists it is recorded against the shared
  `verification_input_establishment_identity` and re-attempted only through that
  identity's **one** accepted-B9 group, which serves the whole episode and every
  caller attached to it.
- **It never lets a content-blind key stand in for a content-bound one.** The
  family key is {declared operation class, declared artifact scope} and nothing
  else; the one-outcome constraint binds to the content-bound
  `verification_generation_identity` alone, and accepted B9's retry groups bind
  to it for a sealed generation and to the **episode-scoped, caller-blind**
  `verification_input_establishment_identity` before a seal — which fences a
  basis and never an outcome — never to `verification_question_identity`, which
  locates and never locks — so a changed
  world, including a changed authority order or ruleset version, is always free
  to be verified as a successor generation of that same family with its own
  single outcome (§5, §9 AIC-4, §11).
- **It never opens a generation before its basis is sealed, and never changes a
  sealed generation's inputs.** No re-proof, declaration, or partial read
  establishes, preassigns, or reserves a `verification_generation_identity`; only
  a fully revalidated, atomically sealed basis does. After the seal, no input is
  re-read, refreshed, or substituted inside that generation: a later file change
  belongs to a later request's re-proof and its successor generation (§6.1, §6.3,
  §9 AIC-0…AIC-4).
- **It never reopens the sealed-basis transaction for an established
  generation.** AIC-1 and AIC-2 are the pre-generation input-establishment seam
  alone and are never executed or re-executed under an existing generation
  identity. An admitted established-generation retry enters at **AIC-3** and runs
  AIC-3 through AIC-5 on the committed sealed basis, binding no new
  input-establishment identity, acquiring no claim, enumerating nothing,
  recomputing no artifact identity, revalidating nothing, sealing nothing,
  replacing no input, and re-deriving no generation identity (§5, §9, §11).
- **It never retries anything itself and never retries a refusal into a pass.**
  Recording which accepted B9 §3 class one of its own durable outcomes supplies
  (§11.1) is **not** admission, not attempt counting, not scheduling, and not
  disposition, and it creates no retry route of any kind: in particular
  `terminal_substantive` is routing terminology that makes a refusal **not**
  machine-retryable, and this seam supplies no substantive-retry policy or
  authorization reference that could make it one. Admission belongs to accepted
  B9 alone; a deterministic refusal is never
  admitted as a technical failure, and a technical failure is never recorded as a
  refusal. A re-attempt under an established generation happens only on confirmed
  unchanged canonical inputs and only across AIC-3 through AIC-5 on that
  generation's sealed basis; otherwise it is a fresh input-establishment
  operation, a successor generation at its seal, and a new group — or it fails
  closed. A pre-generation re-attempt likewise happens only on B9's R1 admission
  under the exact accepted budget reference and recorded schedule class, with no
  second live attempt.
- **It never lets a caller's identity split shared pre-generation work.** The
  caller-blind `verification_input_establishment_identity` is derived from the
  declaration family, the `establishment_episode_anchor`, the exact source
  references to consult, and the operation class and version, and from nothing
  else: two identical concurrent authority checks against the same
  fresh-establishment condition converge on **one** establishment episode, **one**
  live claim, **one** execution of AIC-1/AIC-2, **one** sealed basis, and **one**
  accepted-B9 retry group, while each caller stays separately referenced by its
  own attachment and is never merged or discarded (§5, §9 AIC-0, §10, §17.8).
- **It never lets a shared identity become a stale one.** A completed episode's
  anchor is spent: a later request passes the §6.1 / §6.3 current-input re-proof
  in full before anything committed is released to it, an exhausted or
  early-stopped episode yields no fresh anchor and no minted episode around B9's
  admission, and a changed world commits a new anchor record and opens one new
  shared episode whose fully revalidated seal alone creates the successor
  generation (§5, §6.1, §6.3, §11, §14).
- **It never forces or invents an artifact class.** The named classes are the
  source's required examples; the taxonomy is neither closed nor extended here
  (§4.1).
- **It is not a second gate.** It must not become a parallel implementation of
  any gating, promotion, access, privacy, or write-validation logic
  (`cursorrules` §1A), and it must not become a parallel implementation of retry
  admission, counting, or scheduling. It reports recorded permission state; it
  never enforces it in place of the owning module.
- **It has no write path to any artifact.** Read-only observation plus
  append-only writes to its own records — nothing else.
- **It decides no Register-A policy, invents no threshold, and invents no N.H
  policy of any kind.** It also invents no retry, gap, deadline, budget, or
  expiry value: retry values are consumed as already accepted (§11), and no
  freshness duration exists (§6.1).
- **It never asks Ness to re-decide anything** and puts no question to Ness.
- **DUMB throughout.** It establishes directly-verifiable machine-state and
  provenance facts (Master §0A permits exactly this) and never interprets
  meaning, never closes anything into a fact, and never promotes an
  interpretation.
- **No implementation, no code, no patch, no production store, no marker, no
  seal, no migration.** For this v1_10 artifact, ChatGPT created only the new
  versioned candidate in ChatGPT's file workspace at Ness's explicit request;
  ChatGPT did **not** write into Ness's N.H worktree and performed **no** `git
  add`, `git commit`, `git push`, or `.git` metadata mutation. The intended N.H
  placement remains `05_ACTIVE_CANDIDATE/`; physically placing the delivered
  file there is a separate Ness action. No governing, accepted, historical,
  working, production, store, marker, migration, or unrelated N.H file was
  changed by ChatGPT (§20 item 3, §22).
